Release Notes

Release notes shown to users inside Odoo: what a deployed change means for the people using it, in their words, with buttons that open the new screen.

This module is the engine: the models, the access rules, the screens and the loader. It ships no notes of its own. A project adds a small holder module, <prefix>_release_notes, that keeps the note files and asks the engine to load them (see Configuration).

  • A Release Note (release.note) has a key (usually the ticket, e.g. PROJ-123), a title, a one-line summary, an HTML body, tags and the business models the change is about.
  • Notes are written as files in the holder module’s notes/ folder and loaded on every install or update of that module. The loader only creates notes; it never overwrites one that already exists.
  • A loaded note starts unpublished and is visible to Release Notes managers only. Its Deployed by user publishes it.
  • Publishing sends one OdooBot direct chat to every active internal user who can read at least one of the note’s models. No email is sent, and a note is announced once, however often it is unpublished and published again.
  • Every internal user can open Release Notes to read the published notes, search them and filter or group them by tag.

Why the notes live in a module of their own:

  • The engine depends on mail only and the holder on the engine only, so an update of the holder (-u <prefix>_release_notes) touches no other module of the project.
  • One loader call reads the whole notes/ folder, so a new note adds a file and no manifest entry - parallel pull requests do not conflict on the manifest.
  • Buttons in a note are plain /odoo/action-<module>.<xml_id> links, so a note can point at any module’s screen without a dependency on it.

readme/release_note_flow.puml shows the flow from the pull request to the users’ chats.

Configuration

Holder module

The engine loads nothing by itself. Add one module to the project, named <prefix>_release_notes (acme_release_notes below), made of:

  • __manifest__.py, depending on this module and loading one data file:

    {
    "name": "Acme Release Notes",
    "version": "20.0.1.0.0",
    "author": "Acme",
    "license": "LGPL-3",
    "depends": ["release_notes"],
    "data": ["data/release_note_load.xml"],
}

    Keep author and license: Odoo logs a warning for a manifest that lacks either one.

  • an empty __init__.py;

  • data/release_note_load.xml, calling the loader with the holder’s own name:

    <?xml version="1.0" encoding="utf-8"?>
<odoo>
    <function model="release.note" name="_load_release_notes">
        <value>acme_release_notes</value>
    </function>
</odoo>

  • a notes/ folder with one <key>.html file per note (see Usage);

  • a test that parses every file of notes/ with release.note._parse_release_note_file and checks that no two share a key and that each key is a release note: the loader only skips a file it cannot read, the test fails on it.

Install the holder; it brings the engine with it. Every later update of the holder (-u acme_release_notes) loads the note files whose key is new.

Keep the <function> out of a noupdate block: there it would run on install only, and notes added later would never load.

Access groups (Settings > Users, the Access Rights tab of a user, section Release Notes)

  • Internal users (no group to set) read published notes and their tags. Unpublished notes are hidden from them.
  • Manager sees every note, creates and edits notes, manages tags, sees the Models and Notified fields, can be a note’s Deployed by user and can publish and unpublish. Administrators (role Administrator) are managers through an implied group and are the only users who can delete a note. The group is not a light one: a user who holds it has the role User, not Light.

Deployed by

  • Only a Release Notes manager can be the Deployed by user.
  • It is meant to be whoever ran the deploy. A deploy script can set it; in the form, a manager can set it only to themselves, and only while it is empty.
  • Once it is set, only an administrator can change it.

Tags (Release Notes > Configuration > Tags, managers only)

An editable list of name and colour. Sales, Purchase Orders, Inventory, Manufacturing, Projects, Accounting, HR, Maintenance, Quality, Shipping and CRM ship with the module. A tag named in a note file that does not exist yet is created by the loader; a tag is matched by name regardless of case.

Usage

Write a note (in the pull request of the change): add notes/<key>.html to the project’s holder module (see Configuration) - a front-matter header between two --- lines, then the HTML body:

---
key: PROJ-123
title: Release notes in Odoo
summary: Updates now arrive as an OdooBot chat with a link to the details.
tags: Projects
models: purchase.order, sale.order
---
<h2>What changed</h2>
<p>...</p>
<a class="btn btn-primary" href="/odoo/action-purchase.purchase_rfq">Open Requests for Quotation</a>
  • key and title are required; summary is the line shown in the chat. tags and models are comma-separated; models are technical model names, and a name not installed is skipped.
  • Header names are case-insensitive. The file is read as UTF-8.
  • A button is a link with class="btn btn-primary" and href="/odoo/action-<module>.<action xml_id>".
  • A file the loader cannot read as a note (no header, no key or title, not UTF-8) is skipped and logged as an error, and so is a file declaring a key an earlier file already has. The other notes still load and the module update goes on: a note never stops a deploy.
  • A key that already exists in Odoo is skipped: a later edit of the file does not reach that note. Edit the note in Odoo instead.

Load the notes (the deploy): update the holder module, -u <prefix>_release_notes. Each file with a new key becomes an unpublished note.

Publish a note (the deployer, after the deploy):

  1. Open Release Notes, filter Unpublished and open the note.
  2. Read it and check each button opens the right screen. A manager has the body in the text editor: a click on a button shows its link, and that link opens the screen.
  3. Check Models: they decide who is notified, and publishing needs at least one.
  4. Press Publish.

Rules:

  • Only the note’s Deployed by user can publish it - administrators included. A note without one cannot be published.
  • Published, Published by, Published date and Notified are set only by the buttons; writing them directly is refused.
  • The key cannot be changed after the note is created.
  • Any manager can Unpublish: the note is hidden from users again, the chats already sent stay, and publishing again sends nothing new.

Read notes (every internal user):

  • OdooBot posts New update: <title>, the summary and an Open release note link in a direct chat with each recipient (Discuss).
  • Release Notes lists the published notes, newest first. Search by title, key or summary, filter by tag, or group by Tags.

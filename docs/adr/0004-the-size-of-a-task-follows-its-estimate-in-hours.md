# The size of a task follows its estimate in hours, and a project marks the stages that need a type and an estimate

Status: accepted (2026-11-16), amended (2026-11-20: the creation of the next occurrence of a recurring task is not checked; a change of project that keeps the stage is checked, and the kanban quick create asks for the type and the estimate, that of project sharing included; an estimate given wins over the hours `hr_timesheet` reads from a title; the portal writes the type and the estimate on the tasks of a flagged project only; 2026-11-21: nor does it move a task with them out of one, and the portal's views get them read-only where no other model caches them; a refused quick create of project sharing shows the refusal)

The 16.0 branch decided this first. Its record, `docs/adr/0004-the-size-of-a-task-follows-its-estimate-in-hours.md` there, holds the alternatives it weighed; this one states the decision as it stands on 20.0 and what differs.

**The hours are the estimate.** On this branch they are core's `allocated_hours` (Allocated Time), the field Odoo 20 has in place of `planned_hours`. The size (`tshirt_estimate`, labelled Size) is stored and computed from them: up to 2 h XS, up to 6 h S, up to 12 h M, up to 32 h L, up to 60 h XL, above that XXL; hours not above zero, no size. Neither the type nor the size has a default. A size sent in a `create` or a `write` is ignored and the call goes through; from 20.0.2.15.1 a portal user's call is refused instead, as core refuses any field outside the portal's writable fields (core's portal test of project sharing expects it). From 2026-11-20 the type and the hours are among those fields on the tasks of a flagged project, and the rule's flags (`is_ai_driven`, `is_estimate_required`) among the portal's readable ones: a collaborator with Advanced Edit gives them in the quick create of the shared kanban, which Odoo offers to no one else, one with Edit may write them too (by a call, or with Task Logs in the Allocated Time column of the sub-task list of the sharing form), and one who may only read writes neither. On the tasks of any other project a portal user's create or write naming either is refused (`AccessError`), as core refuses it: the check reads the project the task has once saved, after the call, as the rules do. A portal user's views show both read-only there (below), so that a new task or sub-task does not send them; `fields_get` answers for the model, not for a task, and calls them writable. The hours must be a finite number: a NaN or an infinity is refused in any project.

**The portal does not take them out of a flagged project** (2026-11-21). In Odoo 20 a sub-task that does not show in a project of its own follows the project of its parent (`project_id` is computed from `parent_id`), and a portal user may write `parent_id`, on the sub-task or as a link in the `child_ids` of the new parent. A sub-task given a type or hours in a flagged project could so reach a project where a write of either is refused. A portal user's write that takes a task with a type or hours out of a flagged project into one that is not is refused with the same `AccessError`, the sub-tasks that go with it counted, archived ones included (they follow their parent too); the refusal names those the user may read and only counts the others. It is a refusal, not a clearing of the two fields: the values may be an internal user's, which a silent clearing would lose, and the refusal is the answer the portal gets in that project already. Every other move goes through: between flagged projects, within or between projects that are not flagged, of a task without type and hours, of a task that shows in its own project (it stays there), and any move by an internal user.

**Where the portal's views get them read-only** (2026-11-21). Core caches a model's views under its `_get_view_cache_key`, which for the task holds whether the user is a portal user. The view of another model with a task x2many that has no list of its own gets the list from the task's `_get_view` (`_get_x2many_missing_view_archs`) and is cached under the other model's key, which does not: set in `_get_view`, the read-only of whoever rendered first would reach every user. They are set in `_get_view_postprocessed`, which core runs for the task's own views only, on the arch it caches under the task's key; the inline lists of a task view are part of it. A task list core embeds that way, in a view of the task or of another model, shows them editable to a portal user, refused on save as before; no view of project sharing has one. The alternative was a condition that does not depend on who renders: a field computed per user (portal, project not flagged) named in the `readonly` of every task view. It would hold in an embedded list too, but adds a field and its computation to every task view of every user, for the portal's sake.

**A project marks the stages that need a type and an estimate** (`estimate_required_states`, table `project_estimate_required`, the names of 16.0). A task of a flagged project enters such a stage only with a task type and an estimate above zero. The rule runs where the closing rule of ADR 0002 runs, after it: on a create, and on a change of stage or of project, also one that keeps the stage. An edit of a task that already sits in such a stage is not checked, and templates (a task template, its sub-tasks, the tasks of a project template) are outside the rule, as they are outside the closing rule. So is the creation of the next occurrence of a recurring task, for the reason and by the means ADR 0002 gives.

**The priority star.** Flagged projects rank tasks by Priority Level, so the core star is hidden on their tasks: the form, the kanban card, the list, the lists inside the form and the calendar popover. Its stored value is not touched, and projects that are not flagged keep it, as does the portal.

**What differs from 16.0.**

- No migration and no install hook recompute the sizes of existing tasks (ADR 0001: no database that has to be kept is known to run this branch). A database that has an earlier 20.0 version of this module installed keeps the sizes stored there until the hours of a task change.
- The next occurrence of a recurring task is built by core from a copy of the task, so it carries the type and the hours without an override.
- 16.0 sets hours that are NaN or infinite to zero by a migration. Here a task that got such hours under an earlier 20.0 version keeps them, and the constraint refuses its copies and its next occurrence until they are corrected.
- The three fields 16.0 deletes with a pre-migration (`difficulty`, `knowledge_area_level`, `tester_id`) are deleted here by their declarations alone: the update of the module drops them with their columns.

**Consequences.**

- A task created straight into a marked stage needs its type and its hours in the same create: a mail alias and a task created from a sales order line are refused there, and so is a copy that keeps the stage of a source sitting there without them.
  - 2026-11-20: the kanban quick create of a flagged project shows the type and the estimate, required in the columns of marked stages and optional in the others; where the quick create has a project field (My Tasks) they follow the project picked and its first stage. The required flag is the rule's own answer for the task (`is_estimate_required`), so a template is not asked for them. The web client of Odoo 20 asks for no number field, required or not: an estimate of zero still reaches the rule, which refuses it.
  - 2026-11-20: the quick create of project sharing, offered to a collaborator with Advanced Edit, shows them the same way, the project and the column's stage given as defaults.
  - 2026-11-21: when the server refuses a quick create, core's kanban opens the default form of the task in a dialog, the name carried over: in the backend the task form, which has both fields, and the refusal shows only if that form's save is refused too. Project sharing has no default form it can load (the default one is the internal form, whose view class its web client lacks), so the dialog never opened and the refusal went unseen. There the quick create shows the refusal in the dialog the web client gives that error elsewhere, and stays open with what was typed, to be corrected and added again. Opening the form of project sharing instead was the alternative: it shows neither field, so the collaborator could not answer the refusal there. This covers the quick create of every shared project, since none of them can load that form; the backend keeps core's dialog.
- A recurring task that has no type or no hours is set Done or Cancelled whatever the first stage of its project requires: its next occurrence enters that stage without them, and meets the rule once it is moved into a marked stage.
- A stage listed for a Resolution and for a type and an estimate refuses for the Resolution first.
- 2026-11-21: the portal's move rule is one-way: a portal user may move a sub-task with a type or hours from a project that is not flagged into a flagged one, and is then refused moving it back.
- The star hidden on a task still orders the lists core sorts by it, and core's priority filters remain.
- With Task Logs (`hr_timesheet`) installed, timesheet users also see the same hours as Allocated Time on the tasks of a project that uses timesheets; the two inputs are one field.
  - 2026-11-20: `hr_timesheet` reads hours from a task title such as "Fix 2h" (the inverse of `display_name`, after the stored fields) and writes them over an estimate given in the same create or write. The module gives the task back the estimate given; an estimate of zero is none, and the title's hours stay.

Reversal cost: drop the compute and the rule and make the size editable again.

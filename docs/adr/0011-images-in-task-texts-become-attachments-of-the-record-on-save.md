# Images in task texts become attachments of the record on save

Status: accepted (2026-11-18), amended (2026-11-20: an image the record has is used again, links by this database's host, `srcset` and CSS images, file links of a copy, comments skipped whole, a file gone from the filestore not used again, the host of the record's base url, the original of an edited image)

The 16.0 branch decided this first. Its record, `docs/adr/0011-images-in-task-texts-become-attachments-of-the-task-on-save.md` there, is carried here with what differs on 20.0.

The Html texts of a task, of its question rows and of its test cases can hold their images inline: a tool writing over RPC sends an image as a base64 `data:` URI in the `src` of an `<img>`. Every read of such a text carries the bytes of every image in it: the form, an export, and an agent that reads a task through a connector, whose read grows by the size of each image.

**A save gives the inline images of its texts to the record holding the text.** From 20.0.2.13.0 `project.task.image.mixin`, on the task, the question row and the test case, follows each create and write: an `<img>` whose `src` is a base64 inline image becomes an `ir.attachment` of the record whose text holds it (`res_model` and `res_id` of the task, the row or the test case) with an access token, and the `src` becomes `/web/image/<id>?access_token=<token>`. That is what the html editor does with an image added in the form, and what `mail.message` does with the inline images of a message body. The texts are the stored Html fields that are neither computed nor translated (the column of a translated field holds every language), and from 20.0.2.15.1 the html properties of a task's `task_properties`, the defaults Odoo fills in from the project included: on create and on every change of the task's project, its own or one that follows a parent, its other properties stored as they are. The mover changes only the url and leaves the rest of the text as stored, without a parser serialising it again; the field then sanitizes the new text as on every write (`Field.write`). It applies to every task of the database, in an AI-driven project or not, and to every saver.

Rejected:

- Leave the images inline. Every read stays as heavy as its images, and an agent's read of a task with screenshots is mostly base64.
- The editor's upload alone. It covers an image added in the form, not a tool writing over RPC, a text created by other code or the copy of a text.
- A scheduled job that moves the images later. The texts stay heavy until it runs, and it rewrites records after the fact, as its own user, changing their `write_date` and `write_uid` unless it goes around the ORM.

**The new text is stored without a second write.** The attachments are created after `super()`, under `sudo()` and with the saving user as creator, once the save has passed its own access checks. The new texts are stored through their fields (`Field.write`, then `modified`) and flushed with the save, so tracking sees one save, and no write override of another module runs a second time. On the task the mixin comes below core's classes, `html.field.history.mixin` included, so the description history builds its revision from the moved text.

**Core decides what an image is.** `ir.attachment._check_contents` runs first, on a copy of the values and before the create, not in a savepoint around it: a savepoint flushes, which would run the save's precommit hooks (tracking) and catch their errors. The attachment is then created with `image_no_postprocess`, so core processes each image once. An image core fails to read stays inline and the save passes. `MemoryError`, the CPU time limit of a worker and database errors are raised. Core resizes an image larger than `base.image_autoresize_max_px` (1920x1920 by default), as for every attachment upload, and applies its other attachment rules: an SVG moved by a user who may not edit views is stored as text, and no longer displays.

**A new record copies the images of another record.** A task, a question row or a test case created with a text that links `/web/image/<id>` of an attachment of another task, row or test case gets its own copy of that attachment, with a new token, and its text links the copy: a duplicated task and its copied lines, a task created from a template, the next task of a recurrence, a create from another record's text. A row or a test case moved to another task does the same for the images of other records; its own images stay its own. The copy outlives its source. A write that pastes such a link leaves it, and so does a copy of an image core fails to read or whose file is missing from the filestore. An image the Odoo 20 editor has cropped or converted names, in `data-original-id` and `data-original-src`, the attachment its next edit starts from (2026-11-20): where that original is an attachment of the same record as the image, which the copy may take under the rule of a copy, the new record gets a copy of it too and the two attributes name that copy; otherwise they are dropped with `data-mimetype-before-conversion`, and the next edit starts from the image shown. A copy keeps no `original_id`: core deletes an attachment with its original, so a copy would go with the record it was copied from.

**A copy needs the right to see the image.** A copy hands the image to whoever reads the new record, so it is made only of an image the saving user may see: one they can read, or one whose link carries the attachment's own access token. Under `sudo()`, the superuser included, a read check proves nothing about where the text came from, so only the token counts. A token that is not ASCII, the link's (a percent-encoded one can decode to it) or the attachment's, counts for nothing: `consteq` raises on it, and so does the server's check of such a link. The link's token is read as the server reads its query: the first parameter whose name decodes to `access_token`.

**An image the record has is not attached again.** Before it creates an attachment for an inline image, or copies one of another record, the mover looks for an attachment of the same record (`res_model` and `res_id` of the record holding the text, no `res_field`) with the `checksum` and `mimetype` core would store: those of the contents after `_check_contents`, so the same large image pasted twice compares its resized bytes. It uses that one, and gives it an access token when it has none. Not one posted with a message (in `message_attachment_rel`): a note's attachment belongs to the task too, and deleting the note deletes it, which would break the text; an upload to the attachment box, or the editor's upload of an image, serves. Nor one whose file is missing from the filestore (2026-11-20): core reads it as empty, so the text would link nothing, and the bytes go to a new attachment. It uses only one the saving user may read by their own rights (`has_access("read")` in their environment without `sudo()`), also in a save that runs under `sudo()`, as core saves a portal user's task: the text would otherwise hand them the token and name of an attachment they cannot see. Where none serves, a new attachment holds their bytes. The candidates are tried in order of creation, and the first that serves is used: each is read alone and through its storage (`raw`, which a storage module may override), once the other checks pass, as `raw` read on the candidates as a recordset would read every file of them (2026-11-20). An image pasted again in a later save, or in another text of the same record (an html property of a task included), links the attachment the record has. Another record never shares one, a row and its task included: each keeps its own, deleted with it. The mimetype is part of the match, so an SVG stored as text for a user who may not edit views does not link the SVG image an administrator attached. An attachment used again is not counted in `images` and `bytes`, and a dry run, which creates nothing, counts the same contents once, as the run does.

**A link by this database's host is a link of this database.** An absolute `http(s)://<host>/web/image/<id>` link, or a protocol-relative `//<host>/web/image/<id>`, is copied as a relative link is when it names the host (in any case) of the record's base url, by either scheme: Odoo picks the database by host, not by scheme, and the copy is still made only under the rule of a copy. The base url is the brief's (2026-11-20; before, the `web.base.url` system parameter alone): `get_base_url()` of the task, or of the task of a row or a test case, which website sets to the domain of the company's website and is otherwise `web.base.url`. The link's port and the base url's must be equal, each counted as none where it is the default of its own scheme (of the base url's for a protocol-relative link), written or left out: with the base url on port 8069, a link without a port is another server's. A user part (`user@`) does not count. The url is read as a browser reads it, tabs and line breaks dropped and outer spaces stripped. The rule is the brief's: one helper of `html_markdown` serves both (ADR 0012). The link to the copy is relative. A link to any other host or port stays as it is, and with the base url blank, naming no host after `http(s)://` or `//`, or a port that cannot be read, so does every absolute link. The mover and the brief (ADR 0012) read the id as the editor writes it, at most ten ASCII digits: the mover leaves a link written otherwise as it is.

**An image is read wherever a text shows one.** Besides the `src` of an `<img>`, every url of a `srcset` on `<img>` and `<source>` and every `url(...)` in the `style` of any tag (a `background-image`), quoted or not, is moved or copied the same way. A `srcset` is split as the HTML standard splits it: a url runs to a whitespace, so the comma of a data URI stays in it, and loses its trailing commas; its descriptors (`1x`, `480w`) stay. The values are read unescaped, the new url is written escaped, and every other character of the attribute stays. The shapes are those the Odoo 20 sanitizers keep, as on 16.0: `description` (`sanitize_attributes=False`) keeps `srcset` and `style`, the other texts and the html properties keep `style` only, and `<picture>`, not on the tag whitelist, is dropped around its `<source>`. Comments are kept, but for one that opens the text, and from 2026-11-20 skipped whole: an image or a link a comment holds is neither moved nor copied, and a comment left open runs to the end of the text. The tags and comments are read by a pattern that runs in linear time over unclosed tags and comments, and a decimal character reference past the last code point reads as U+FFFD, as `html.unescape` gives it, without the `int()` that refuses more than 4300 digits.

**A copy links its own copy of a file.** The editor links an uploaded file as `/web/content/<id>?unique=<checksum>&download=true&access_token=<token>`, its attachment on the record edited. Where a new record copies images, an `<a href>` to `/web/content/<id>` (the id followed by `/`, `?`, `#` or nothing) of another record's attachment, relative or by this database's host and readable under the rule of an image, becomes a copy on the new record, or the attachment the record has with the same contents. The other forms the brief reads (`/web/content/ir.attachment/<id>/datas`, `?id=<id>`) stay as they are: nothing in Odoo 20 writes them into these texts. The link keeps its path, query and fragment with the id of that attachment (`unique` stays: the bytes are the same), and its access token comes last, in place of every parameter whose name decodes to `access_token`. The editor puts the link in a file box, `<span class="o_file_box" data-attachment-id="<id>">`, whose icon opens the attachment the box names, without a token: a box that names an attachment a link of the same text was copied from names the copy, the rest of the text as it is. The file is copied as uploaded, without core's resize of a large image (`image_no_postprocess`): a download is not a picture shown. Core's rule that markup (HTML, SVG) is stored as text for a user who may not edit views still applies, so a copy cannot turn a file into a page served to its readers.

**Old texts move through one method.** 20.0.2.13.0 has no migration. `project.task._move_inline_images_to_attachments(dry_run=False, store=True)` moves the inline images of the texts of tasks and of their rows with the mover a save uses, for a migration or a one-time script, run over the tasks in batches: it holds every new text until it returns. It returns the counts `records`, `images` and `bytes`; a dry run counts as a run would. `store=False` returns the new texts without storing them, so that a caller stores them by SQL and keeps `write_date` and `write_uid`.

**What differs on 20.0.**

- The Odoo 20 html field uploads an image added in the editor when the record is saved, through `/html_editor/attachment/add_data`, as an attachment of the record being edited, and links it with an access token. The mixin covers what the editor does not: a text written over RPC or by other code, the copies of a text, a line moved to another task, and texts saved before.
- The record holding the text owns the image, as the editor attaches it: an image of a question row or a test case is an attachment of the row. On 16.0 every image is an attachment of the task. A link to an image of any other record of the three models is copied; on 16.0, a link to another task's image.
- A row's images are deleted with the row. A task deleted takes its own images, and deletes its rows through the ORM, under `sudo()` once its own access check passed, so their images go with them: the database cascade would leave them.
- The read check of a copy, and of an attachment used again, is `has_access("read")`, on 16.0 `check("read")`. The attachment is created with `image_no_postprocess` after `_check_contents`; on 16.0 its create processes the image a second time.
- An attachment is used again by the record that owns it: on 16.0 by the task and its rows together. Core's `create_unique` does not serve: it reuses an attachment of any record, one of a message included, that the user may write.
- The editor links an image it uploads as `/web/image/<id>-<unique>/<name>?access_token=<token>`, which the mover reads as `/web/image/<id>`.
- werkzeug 3 decodes a query leaving invalid UTF-8 percent-encoded (`%ff` reads `%FF`), where the werkzeug of 16.0 puts a replacement character: the mover reads a link's token the same way.
- Core stores markup given as an image and a truncated TIFF as they come, without resizing them, so they become attachments. On 16.0 core fails to read them and they stay inline. A decompression bomb stays inline on both.

**Consequences.**

- The images of a task's Description and Solution show among the attachments of the task's chatter and are deleted with the task. The images of a row are attachments of the row. An image taken out of a text stays an attachment of its record.
- The link carries an access token: whoever holds it sees the image, as with the images of a message.
- One image is one attachment of its record: pasted again, in any text of the record, it links the one the record has. A large image a copy both shows and links as a file gives two: the image resized, the file as uploaded.
- A link to another host stays a link to it. An image in another attribute (a `poster`, a `data-*` other than the original of an edited image) or in a comment or in a `<style>` element (dropped by the sanitizer) is not read, and a file link is copied only where a new record copies images: a write that pastes one leaves it.
- Texts saved before 20.0.2.13.0 keep their inline images until they are saved again or the method runs on their task.

Reversal cost: drop the mixin from the three models. Texts already moved keep their links, which work as long as their attachments exist; putting the images back inline takes a script.

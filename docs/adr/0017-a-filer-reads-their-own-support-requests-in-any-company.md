# A filer reads their own support requests in any company, through a read-only exception to the company rule of tasks

Status: accepted (2026-11-19)

A support request is a task of the project flagged Develops This Odoo, created in that project's company, the filer its UAT user (`project_support_request`). Odoo's company rule of tasks, `project.task_comp_rule`, is global: a user reads a task only in the companies selected in the company switcher. A filer working in another company filed a request and then could not open it: the form answered with an access error, and *View Closed* listed nothing. Many users may not select the company of the support project at all.

**The decision.** From `project_support_request` 16.0.1.1.0 a task is read when core's company rule of tasks takes it (as shipped: when its company is selected), or when it is a task of the project that Develops This Odoo and the reading user, an internal one, is one of its UAT users. The request opens and is listed, from the Support item and anywhere else, whatever the user's company selection, and the selection is left alone. Requests stay created in the company of the support project.

**Mechanism.** Global rules are AND-ed, so a group rule cannot widen the company rule: the module splits it. Core's record keeps its domain and its write, create and delete, and loses its read; the module's own global rule `project_task_rule_company_read` reads. Its domain is a call, `user._support_request_task_read_domain()`, which evaluates the domain core's rule has at that moment with ir.rule's own evaluation context (the selected companies included) and returns it OR-ed with the exception: a task of the flagged project with the user among `uat_user_ids`, for an internal user only. ir.rule caches the evaluated domain per user and selected companies, and every write of a rule clears that cache: an edit of core's domain applies to reading at once, as it does to writing.

Core's rule given groups is a group rule, which core applies to the members of those groups only: for a user outside them the method returns no restriction, as core's rule does not restrict their writes either. A member gets core's domain and the exception, in a global rule: for reading, Odoo combines it with every other rule by AND, while for writing it combines core's rule with the member's other group rules of tasks by OR. Where another group rule takes tasks of other companies, a member may write them but reads only the tasks of the companies they selected and their own requests, which may be fewer tasks than they read before the install.

With core's rule archived or deleted, reads keep the domain `project` ships it with, `[('company_id', 'in', company_ids)]`, and the exception. They keep it for every user, whatever groups the archived rule has: the method checks the archive first, so a user outside those groups, unrestricted while the rule was active, reads by that domain too, and the module fails closed. The module lifts the company restriction of reads for its exception only, never altogether: an administrator who lifts it for tasks archives the module's rule as well. This holds from the install on: a database that had lifted the restriction before installing, by unticking Read on core's rule or by archiving or deleting it, reads by the module's rule once installed, and archives that rule after installing to read as before.

Core's rule is a `noupdate` record of `project`, so a record of this module naming it would be skipped on update: a `<function>` of the data file calls `ir.rule._support_request_split_task_company_rule()` at every install and update, which takes core's read off and leaves the same state however often it runs. It leaves a deleted rule alone, and a rule whose only permission is Read, since a rule keeps one (`no_access_rights`); it logs a warning, and reads then stay as core's rule has them, without the exception. The `uninstall_hook` gives core's rule its read back, and with it every active global rule of tasks without Read that is taken for a copy of core's: a Duplicate made while the module is installed carries Read off, and with the original archived it would leave reads of tasks without the company restriction once the module is gone. A copy is taken by core's domain, as it stands or as `project` ships it, or by a name starting with core's, never by a domain calling the module's method, and the hook logs the rules it gave Read back to. The hook does not tell a read the module took off from one an administrator took off, before the install or after: it restores these rules as `project` ships its own, with Read, so a database that had unticked Read on core's rule, or kept a copy of it without Read, before installing gets Read back on them and unticks it again after the uninstall. It also archives the active rules of tasks whose domain calls `_support_request_task_read_domain`: copies an administrator made of the module's rule, whose domain no longer evaluates once the module is gone. The module's rule goes with its data.

**What it allows.**

- Reading only. Write, create and delete keep the plain company rule: outside the selected companies the filer does not change or delete the request. Where the filer has write access to their own requests, the form there looks editable, since it does not know the rules, and saving is refused. Messages post, since a task takes posts from whoever reads it (`_mail_post_access`), and so do files attached in *Send message*, which the post links to the task as superuser. A file attached with the chatter's paperclip is created on the task directly, which needs write on it, and is refused. Its attachments and followers read with the task.
- The filer's own requests only. Another user's request and a task of another project, the filer a UAT user of it or not, stay behind the company rule. Every other rule still applies: the project's visibility and, under `project_member_access`, its access mode.
- Not the project. The form shows the names of the project, the stage and the company (Odoo reads the names of linked records as superuser), but opening the project is refused in a company the user did not select.
- Nothing for a portal or other share user, a UAT user or not.

**Rejected.**

- Switching companies: the Support item added the request's company to the selection before opening it, as a link in a notification mail does. It changes what the user sees in every other screen, and fails for a user who may not select that company.
- A notice only: filing the request and telling the user they cannot open it. The filer could not follow what they filed.
- Widening the domain of core's rule: write, create and delete would widen with it.
- A copy of core's domain in the module's rule: a database that changed core's domain would read by the stock one and write by its own, and each update of the module would set the copy back.
- Creating the request in the filer's company: the project's company decides the company of its tasks.
- No company restriction of reads with core's rule archived or deleted, as without the module. An administrator who duplicates core's rule to edit the copy and archives the original gets a copy without read, since the module took it off the original, and the reads of tasks of every company would open after steps that, before the install, kept them restricted.

**Consequences.**

- Every search on tasks carries the exception's two subqueries, on the flagged project and on the UAT users, for every internal user.
- A filer's requests show in any task list whose domain takes them, not only from the Support item.
- A read flag set on core's rule by hand is set off again by the next update of the module.
- While core's rule is global, reading and writing follow one domain, core's, whatever a database changes in it; only the exception is the module's. Given groups, core's rule restricts the writes of its members OR-ed with their other group rules of tasks, and their reads AND-ed with every other rule: members may read fewer tasks than they write, and fewer than before the install. Archiving or deleting core's rule lifts the company restriction from writing only, and a copy of core's rule made after the install restricts writing only: reads keep project's domain, for every user, until the module's rule is archived too.
- A database that had lifted the company restriction from reading tasks before the install has it again once installed, until it archives the module's rule.
- ADR 0013 rejected rewriting core's rules because an uninstall would leave them naming fields that no longer exist. Here core's domain stays as it is; only its read flag changes, and the uninstall gives it back, as `project` ships it, also to a database that had taken it off before the install.

Reversal cost: uninstall the module, or drop its data file and give core's rule its read back; filers then read their requests only in the company of the support project again.

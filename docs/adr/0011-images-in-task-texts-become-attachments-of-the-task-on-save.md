# Images in task texts become attachments of the task on save

Status: accepted (2026-11-17), amended (2026-11-20: an image the task has is used again, links by this database's host, `srcset` and CSS images, file links of a copy)

The Html texts of a task, of its question rows and of its test cases held their images inline: the 16.0 editor puts a pasted or dropped image into the text as a base64 `data:` URI, and a tool writing over RPC sends the same. Every read of such a text carries the bytes of every image in it: the form, an export, and an agent that reads a task through a connector, whose read grows by the size of each image.

**A save gives the inline images of its texts to the task, as core mail does.** From 16.0.2.13.0 `project.task.image.mixin`, on the task, the question row and the test case, follows each create and write: an `<img>` whose `src` is a base64 inline image becomes an `ir.attachment` of the task (`res_model` `project.task`, `res_id` the task, also for an image of a row) with an access token, and the `src` becomes `/web/image/<id>?access_token=<token>`. That is what `mail.message` does with the inline images of a message body. The texts are the stored Html fields that are neither computed nor translated (the column of a translated field holds every language). Only the url changes: the rest of the text is kept as stored, not serialised again by a parser. It applies to every task of the database, in an AI-driven project or not, and to every saver.

Rejected:

- Leave the images inline. Every read stays as heavy as its images, and an agent's read of a task with screenshots is mostly base64.
- An upload in the client only. The 16.0 editor uploads an image it modifies, not one pasted, and a change to the editor covers neither a tool writing over RPC nor a text created outside the form.
- A scheduled job that moves the images later. The texts stay heavy until it runs, and it rewrites tasks after the fact, as its own user, changing their `write_date` and `write_uid` unless it goes around the ORM.

**The new text is stored without a second write.** The attachments are created after `super()`, under `sudo()` and with the saving user as creator, once the save has passed its own access checks. The new texts are stored through their fields (`Field.write`, then `modified`) and flushed with the save, so tracking sees one save, and no write override of another module runs a second time.

**Core decides what an image is.** `ir.attachment._check_contents` runs first, on a copy of the values and before the create, not in a savepoint around it: a savepoint flushes, which would run the save's precommit hooks (tracking) and catch their errors. An image core cannot read (markup, a decompression bomb, a truncated file) stays inline and the save passes. `MemoryError`, the CPU time limit of a worker and database errors are raised. Core resizes an image larger than `base.image_autoresize_max_px` (1920x1920 by default), as for every attachment upload, and applies its other attachment rules: an SVG is stored as text for a user who may not edit views.

**A new record copies the images of another task.** A task, a question row or a test case created with a text that links `/web/image/<id>` of another task's attachment gets its own copy of that attachment, with a new token, and its text links the copy: a duplicated task, the next task of a recurrence, a create from another task's text. A row moved to another task does the same. The copy outlives the source task, whose deletion deletes its attachments. A write that pastes such a link leaves it.

**A copy needs the right to see the image.** A copy hands the image to whoever reads the new record, so it is made only of an image the saving user may see: one they can read, or one whose link carries the attachment's own access token. Under `sudo()`, the superuser included, a read check proves nothing about where the text came from, so only the token counts. A token that is not ASCII, the link's (a percent-encoded one can decode to it) or the attachment's, matches nothing, as on the server.

**An image the task has is not attached again.** Before it creates an attachment for an inline image, or copies one of another task, the mover looks for an attachment of the same task (`res_model` `project.task`, `res_id` the task, no `res_field`) with the `checksum` and `mimetype` core would store: those of the contents after `_check_contents`, so the same large image pasted twice compares its resized bytes. It uses that one, and gives it an access token when it has none. Not one posted with a message (in `message_attachment_rel`): a note's attachment belongs to the task too, and deleting the note deletes it, which would break the text; an upload to the attachment box serves. It uses only one the saving user may read by their own rights (`check('read')` without `sudo()`), also in a save that runs under `sudo()`, as core saves a portal user's task: the text would otherwise hand them the token and name of an attachment they cannot see. Where they may not read it, a new attachment holds their bytes. An image pasted again in a later save, in another text of the task or in one of its question rows or test cases, links the attachment the task has. Another task never shares one: each keeps its own, deleted with it. The mimetype is part of the match, so an SVG stored as text for a user who may not edit views does not link the SVG image an administrator attached. An attachment used again is not counted in `images` and `bytes`, and a dry run, which creates nothing, counts the same contents once, as the run does.

**A link by this database's host is a link of this database.** An absolute `http(s)://<host>/web/image/<id>` link, or a protocol-relative `//<host>/web/image/<id>`, is copied as a relative link is when it names the host (in any case) of the `web.base.url` system parameter, by either scheme: Odoo picks the database by host, not by scheme, and the copy is still made only under the rule of a copy. The link's port and `web.base.url`'s must be equal, each counted as none where it is the default of its own scheme (of `web.base.url`'s for a protocol-relative link), written or left out: with `web.base.url` on port 8069, a link without a port is another server's. A user part (`user@`) does not count. The url is read as a browser reads it, tabs and line breaks dropped and outer spaces stripped. The rule is the brief's: one helper of `html_markdown` serves both (ADR 0012). The link to the copy is relative. A link to any other host or port stays as it is, and with `web.base.url` blank, naming no host after `http(s)://` or `//`, or a port that cannot be read, so does every absolute link. The mover and the brief (ADR 0012) read the id as the editor writes it, at most ten ASCII digits: the mover leaves a link written otherwise as it is.

**An image is read wherever a text shows one.** Besides the `src` of an `<img>`, every url of a `srcset` on `<img>` and `<source>` and every `url(...)` in the `style` of any tag (a `background-image`), quoted or not, is moved or copied the same way. A `srcset` is split as the HTML standard splits it: a url runs to a whitespace, so the comma of a data URI stays in it, and loses its trailing commas; its descriptors (`1x`, `480w`) stay. The values are read unescaped, the new url is written escaped, and every other character of the attribute stays. The shapes are those the sanitizers keep: `description` (`sanitize_attributes=False`) keeps `srcset` and `style`, the other texts keep `style` only, and `<picture>`, not on the tag whitelist, is dropped around its `<source>`. A character reference is read as `html.unescape` reads it, without its `int()` on a decimal one of more than seven significant digits (U+FFFD, past U+10FFFF): a tag inside a kept comment could otherwise hold thousands of digits.

**A copy links its own copy of a file.** The 16.0 editor links an uploaded file as `/web/content/<id>?unique=<checksum>&download=true&access_token=<token>`, its attachment on the task. Where a new record copies images, an `<a href>` to `/web/content/<id>` (the id followed by `/`, `?`, `#` or nothing) of another task's attachment, relative or by this database's host and readable under the rule of an image, becomes a copy on the new task, or the attachment the task has with the same contents. The other forms the brief reads (`/web/content/ir.attachment/<id>/datas`, `?id=<id>`) stay as they are: nothing in 16.0 writes them into a task text. The link keeps its path, query and fragment with the id of that attachment (`unique` stays: the bytes are the same), and its access token comes last, in place of every parameter whose name decodes to `access_token`. The file is copied as uploaded, without core's resize of a large image (`image_no_postprocess`): a download is not a picture shown. Core's rule that markup (HTML, SVG) is stored as text for a user who may not edit views still applies, so a copy cannot turn a file into a page served to its readers.

**Old texts move through one method.** 16.0.2.13.0 has no migration. `project.task._move_inline_images_to_attachments(dry_run=False, store=True)` moves the inline images of the texts of tasks and of their rows with the mover a save uses, for a migration or a one-time script. It returns the counts `records`, `images` and `bytes`; a dry run counts as a run would. `store=False` returns the new texts without storing them, so that a caller stores them by SQL and keeps `write_date` and `write_uid`.

**Consequences.**

- The images show among the attachments of the task's chatter and are deleted with the task. An image taken out of a text, or of a deleted row, stays on the task.
- The link carries an access token: whoever holds it sees the image, as with the images of a message.
- One image is one attachment of its task: pasted again, in any text of the task or of its rows, it links the one the task has. A large image a copy both shows and links as a file gives two: the image resized, the file as uploaded.
- A link to another host stays a link to it. An image in another attribute (a `poster`, a `data-*`) or in a `<style>` element (dropped by the sanitizer) is not read, and a file link is copied only where a new record copies images: a write that pastes one leaves it.
- Texts saved before 16.0.2.13.0 keep their inline images until they are saved again or the method runs on their task.

Reversal cost: drop the mixin from the three models. Texts already moved keep their links, which work as long as their attachments exist; putting the images back inline takes a script.

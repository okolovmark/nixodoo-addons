Project AI-driven

Additions to project tasks for AI-driven development: task attributes, clarifying questions with their answers and the technical solution, a checklist and test cases per task, pull requests as records, and a Resolution that a task needs to enter the stages its project marks. The module also logs the stage changes of every task of the database.

Task attributes (project.task)

  • Priority (Highest to Lowest), T-shirt Estimate (XS = 1h or less, S = 4h, M = 1d, L = 3d, XL = 1w, XXL = 2w or more), Task Type (Feature, Bug, Improvement, Investigation, Milestone, Support, Technical Debt), Difficulty and Knowledge Area Level, next to the tags on the task form. The type is also a column of the task list; its tracking messages name the field AI-driven Task Type.
  • Picking a T-shirt estimate fills Initially Planned Hours while it is empty: 1, 4, 8, 24, 40 or 80 hours. The value is kept only where that field is on the task form, which is the case once Timesheets is installed.
  • A Technical Solution tab with Questions, Answers and Solution, shown to project users on the tasks of a project flagged AI-driven Project.
  • Assignment notifications honour the mail_auto_subscribe_no_notify context, so an account without an email address (an RPC service account) can assign tasks without failing.

Checklist (project.task.subtask)

Task-level checklist items with a description, an Assigned to user, a Reviewer (the creator), a deadline and a state: TODO, Waiting, Done, Cancelled. Only the reviewer and the assignee may change an item’s state or description. Every creation, state, name or assignee change posts a message to the task addressed to the reviewer and/or the assignee, under the internal All checklist updates subtype (a change on an item whose reviewer and assignee are both the current user is a plain note instead). The subtype is not subscribed by default: other followers receive these posts only after opting into All checklist updates on the task or on its project. The same context key silences these posts for an account without an email address. The task’s kanban card shows the current user’s completion percentage over their non-cancelled items and the number of their TODO and Waiting items. The Checklist menu opens on your own TODO items (the My and TODO filters are on by default); remove those filters to see all items.

Test cases (project.task.testcase)

Ordered test cases per task with Steps to execute, Expected results, Comments, a Passed flag and the same four states. The task carries a Tester, general comments and a completion percentage over non-cancelled cases. The Test Cases menu opens filtered on the cases still in TODO; remove the TODO filter to see them all. Copying a task also copies its checklist items and test cases, keeping their states.

Pull requests (project.pull.request)

A pull request is a record of its own, shared by every task it belongs to:

  • URL, required and unique, stored in canonical form: scheme and host in lower case, then the path as written, up to and including the number. /files, a query, a fragment or a closing slash after the number are dropped.
  • Repository and Number, read from the URL. The record is named <repository>#<number>, for example owner/repo#12, and is found by that name or by a part of its URL.
  • State: Open, Merged or Closed. A new record is Open; one created by the conversion described under Installation has no state.
  • Merge Date, Deploy Date and the Tasks it is linked to.

A pull request link is an http(s) URL with a repository path followed by /pull/N, /merge_requests/N (also /-/merge_requests/N), /pull-requests/N or /pulls/N, N being a number of at most nine digits.

Internal users read pull requests; Project / User also creates and edits them. No access right allows deleting one, and portal users have no access.

Pull requests and Resolution on a task (project.task)

  • Pull Requests (pull_request_ids): the pull requests of the task, on a tab of their own on the tasks of an AI-driven project.
  • Resolution (resolution): how the task was closed: Code, Data, Configuration or No change. It is shown on the tasks of an AI-driven project, and its changes are tracked in the chatter.
  • First Pull Request (pr_uri) reads the link of the task’s first pull request, the one created first, and is empty when the task has none. It is on no view of this module. It is stored, so it can be searched, its changes are tracked in the chatter, and it is writable for the tools that write it over RPC. Writing one pull request link finds the record with that link or creates it, and adds it to the task; a link the task already has changes nothing, and neither does an empty value. Anything that is not exactly one pull request link (other text, a link without http(s)://, a commit or branch link, two links) is refused: a task closed without a pull request takes the Resolution Data, Configuration or No change instead.
  • PR (old value) (pr_legacy), read-only: the whole text pr_uri held before the conversion described under Installation, where that text was anything but one plain pull request link.
  • A duplicated task starts without pull requests, Resolution and old value. A copy that keeps the stage of its source, as every task and subtask of a duplicated project does, takes the Resolution and the pull requests of its source.

The closing rule

On an AI-driven project, Stages Requiring a Resolution (pr_required_states) marks stages. A task of that project enters a marked stage only with a Resolution:

Resolution Pull request Result
empty none refused: choose a Resolution
empty present let through, Resolution = Code
Code none refused: add a pull request
Code present let through
Data, Configuration, No change none let through
Data, Configuration, No change present let through, pull request kept

The rule is checked when the stage of the task changes: on creation, on a write of the stage and on a change of project that moves the task to another stage. The Resolution and the pull request may come in the same write as the stage. Any other stage, a project that is not flagged AI-driven and a write that leaves the stage as it is let everything through, so a task already sitting in a marked stage stays editable. No context key skips the rule.

The stage log (project.task.stage.log)

One row when a task is created with a stage and one row on every change of its stored stage, for every task of the database, in an AI-driven project or not. The rows are written by SQL where the row of the task is written, so no context (tracking_disable, mail_notrack, mail_create_nolog) and no sudo() goes around the log, and a stage recomputed by a change of project is logged too, on the task and on the subtasks moved with it.

  • Task, Date and User: the task, when its stage changed and who changed it. The user is empty when it is not known. Deleting a task deletes its rows.
  • Stage and Stage Name: the stage the task entered. The stage is empty when the task left its stage, and when the stage was deleted since; a deleted stage keeps its name.
  • Previous Stage: the stage the task left. It is empty when there was none, when it is not known and when it was deleted since.
  • Source: Recorded for a row written with the change; From the chatter, From the last stage update or From the creation date for a row of the past, filled as described under Installation.

A task created without a stage gets no row. A task that loses its stage gets a row with an empty stage. A write that carries the stage the task already has writes no row.

Only system administrators read the log, and no access right allows creating, changing or deleting a row. The log has no view and no menu. A search of the log first flushes the stage changes that are pending.

Installation

A database that has neither project_software nor kaertech_project_software installed needs nothing beyond installing the module. What a database that has project_task_pull_request installed needs on top of that is under Coming from project_task_pull_request. What the install and the update to 16.0.2.2.0 write to the stage log for the tasks that exist is under Filling the stage log.

Upgrading from project_software

project_software remains for one release as an empty module that depends on this one, so updating it installs this module. Before any data file is loaded, the pre_init_hook takes over everything project_software owns: models, fields, views, access rights, menus and message subtypes keep their database ids, so checklist items, test cases, field values and follower subscriptions stay as they are. It renames the flag where the database stores it: the column, the field on every model that has it, and the view archs, record rule domains, filters and window actions that name it.

What the upgrade needs:

  • addons.yaml lists both modules for that release, also when it pins a commit.
  • The deploy runs an update of project_software (-u project_software) with the server stopped: the hook renames the flag’s column, which running code still reads. A restart without the update leaves project_software and the modules that depend on it unloaded.
  • A module that depends on project_software switches, in the same deploy, its dependency and its external id references to project_ai_driven and the flag to is_ai_driven. The hook rewrites its stored views; data files with the former name would write it back. The view project_project_view_form_inherit_software is now project_project_view_form_inherit_ai_driven.
  • Text naming the flag elsewhere (server action code, automated action domains, export templates) is not rewritten: change it by hand.
  • project_software is uninstalled, once no installed module depends on it, before the release that removes it, and dropped from addons.yaml.

A dependent module that is renamed as well can call three functions of odoo.addons.project_ai_driven.hooks from its own pre_init_hook:

  • is_installed(cr, module_name): whether a module is installed or marked for upgrade.
  • take_over_module(cr, former, module): moves to module everything former owns: external ids, constraints, many2many tables and the views loaded from its files. The caller clears the registry caches.
  • rename_external_ids(cr, module, renamed_names): renames external ids of module from a {former name: new name} dict.

Upgrading from kaertech_project_software

On a database from before the features were cut from kaertech_project_software, where project_software was never installed, the hook takes over only what moved here and renames the flag the same way.

Coming from project_task_pull_request

This module declares pr_uri on the task and pr_required_states on the project and the task under the names, the column and the relation table of OCA project_task_pull_request, and takes its place. The stages marked on each project stay marked, the tracking history of pr_uri stays on the field, and whatever reads pr_uri or writes a pull request link to it keeps working. pr_uri takes one pull request link and no other text: a tool that writes a note there for a task without a pull request sets resolution instead.

The text project_task_pull_request stored in pr_uri is converted when this module is updated to 16.0.2.1.0 (migration script) or installed (post_init_hook):

Old value Becomes
one pull request link, whatever the case of its scheme and host, with or without spaces around it and a closing slash a pull request on the task, Resolution Code
several pull request links one pull request per link, Resolution Code, old value kept
a pull request link without https:// a pull request with https:// added, Resolution Code, old value kept
a pull request link with more after the number (/files, a commit, words) or an invisible character before it the pull request itself, Resolution Code, old value kept
a link that is not a pull request link (commit, branch, repository, another site, no repository before /pull/N, a number of more than nine digits) no pull request, old value kept
a memory:// reference or any other text no pull request, old value kept
empty nothing

Old value kept means the whole text is in PR (old value) (pr_legacy). Nothing is guessed: a pull request created by the conversion has no state, one that already exists is linked as it is, and the Resolution is set to Code only where it is empty. The same link on several tasks gives one pull request. Afterwards pr_uri reads the task’s first pull request, or is empty. Archived tasks are converted too. The tasks are written by SQL, so their last update date does not change, no tracking message is posted and no constraint runs. The log of the update gives the number of values of each kind; a second run converts nothing.

This module does not depend on project_task_pull_request and does not uninstall it. A module that depended on it, or an administrator, uninstalls it once this version is installed, not before: the fields and the relation table stay only because this module declares them too. While it is installed, its constraint requires a non-empty pr_uri in the marked stages of every project, AI-driven or not, so a task without a pull request cannot enter them, whatever its Resolution.

Its code leaves the addons path in the deploy that uninstalls it. While the code is there, the labels stored for the shared fields are its own, PR URI and PR Required States, and they stay until the first update after it is gone.

Filling the stage log

The tasks that exist get the past of their stages in the stage log when this module is updated to 16.0.2.2.0 (migration script) or installed (post_init_hook). One SQL statement inserts the rows of every task that has none, archived tasks included, and writes nothing on the tasks:

Task Rows
with stage changes of its own in the chatter the stage it was created in, then one row per tracked change, all From the chatter
the same, when the last tracked change does not end at the stage the task is in one more row: that stage, empty for a task that is in none, at the last stage update, without a user, From the last stage update
in a stage, without such changes, last stage update 2 seconds or more after its creation one row at the last stage update, without a user, From the last stage update
in a stage, without such changes, otherwise one row at its creation, by its creator, From the creation date
without a stage and without such changes nothing

The stage a task was created in is the old value of its first tracked change, when that is a stage. Its row is dated at the creation of the task, or at that first change when it is dated earlier, and its user is the creator of the task. A tracked change keeps the date of its message and the stage names the chatter tracked; its user is the user of the author of the message, the one with the lowest id when the author has several, none when the author has no user. The stage changes of a predecessor, which Odoo posts on the dependent tasks, are not changes of the task and are left out.

Nothing is guessed. A tracked change that does not start where the one before ended stays as tracked. The row for the current stage is left out when the last stage update is missing or earlier than the last tracked change, and so is any row that would have no date. The fill writes one line to the server log with the number of rows of each case and of the rows left out; a second run inserts nothing.

Run the update with the server stopped. A worker that still runs the previous code changes stages without writing a row, and the fill skips a task that has rows, so such a change stays out of the log.

Configuration

  • On a project, tick AI-driven Project (Settings tab, above Visibility) to show the Technical Solution and Pull Requests tabs and the Resolution on its tasks.
  • Below it, on an AI-driven project, Stages Requiring a Resolution lists the stages a task enters only with a Resolution, and with a pull request when the Resolution is Code. Only stages of the project can be picked. Leave it empty to switch the closing rule off.
  • Checklist items and test cases are managed by Project / User. The Checklist, Test Cases and Technical Solution tabs are hidden from users without that group.
  • Pull requests are read by every internal user and created and edited by Project / User. No access right allows deleting one.
  • The stage log is read by Administration / Settings only. No access right allows creating, changing or deleting a row.
  • To be notified of checklist items that are neither assigned to you nor created by you, edit your follower subscription on the task or on the project and tick All checklist updates.
  • An integration that writes tasks or checklist items with an account that has no email address passes mail_auto_subscribe_no_notify in the context; without it Odoo refuses to send the notification and the write fails.

Usage

On the task form:

  • Set Priority, T-shirt Estimate, Task Type, Difficulty and Knowledge Area Level next to the tags.
  • Checklist tab: add items, each with an Assigned to user and an optional deadline. The assignee or the reviewer moves an item with the state icons (TODO, Waiting, Done, Cancelled). The task’s kanban card shows your own completion percentage, only when you have non-cancelled items assigned to you.
  • Test Cases tab: add ordered cases with steps and expected results, set the Tester, then move each case with the state icons. Marking a case Done ticks Passed; any other state, Cancelled included, clears it.
  • Technical Solution tab (AI-driven projects): record the Questions, the Answers and the Solution.
  • Pull Requests tab (AI-driven projects): add the pull requests of the task, each with its link, state, merge date and deploy date. A pull request already recorded for another task is picked from the list instead of being created again. PR (old value) shows above the list on a task that has one.
  • Resolution (AI-driven projects), next to the tags: choose it before moving the task to a stage that requires one. Code needs a pull request on the task; a task that already has one gets Code by itself.

Project > Checklist lists the checklist items of all tasks, opened on your own TODO items. Project > Test Cases lists the test cases of all tasks, opened on the ones still in TODO.

Project > Pull Requests lists the pull requests of all tasks, the newest first: a list, cards on a phone. Search by URL, repository or task, filter on Open, Merged, Closed or No State, group by repository or state. On the form of a pull request, set State, Merge Date and Deploy Date when it is merged and deployed.

A tool that writes over RPC sets pr_uri on the task to the link of the pull request, one link per write, or resolution to data, configuration or no_change when there is none. A write of another link adds a second pull request to the task.

The stage log has no view and no menu. A system administrator reads project.task.stage.log over RPC: the rows come ordered by date, each with task_id, previous_stage_id, stage_id, stage_name, date, user_id and source (live, tracking, stage_date or creation). The log holds the stages of every task, so code that shows it to other users reads it with sudo(), for the tasks those users can read.

Known issues / Roadmap

  • The path of a pull request link is stored as written. Two spellings of one pull request (Owner/Repo and owner/repo, http and https, with and without /-/) are two records.
  • Nothing reads a pull request from its host: State, Merge Date and Deploy Date are set by hand or over RPC.
  • The pull requests of a task are tracked only through pr_uri: one that is added without becoming the task’s first leaves no trace in the chatter. Odoo 16 tracks no many2many field.
  • The closing rule is checked on the tasks of a write that names their stage or their project. A stage recomputed for another reason is not checked, as for a subtask whose parent changes project.
  • A module that writes a task’s new project on its own, before the other values of the same write, runs the closing rule before the Resolution of that write arrives. Setting the Resolution in an earlier write avoids it.
  • The closing rule is not run when a stage gets marked or a project gets flagged, so a task can sit in a marked stage with neither a Resolution nor a pull request. Such a task stops the duplication of its project until it gets one.
  • A row of the stage log is written when the change of stage is flushed to the database. Several changes of a task’s stage within one flush are one row, from the stored stage to the last one, and a change undone within one flush leaves none.
  • A stage written by raw SQL is not logged.
  • The user of a recorded row is the one the update leaves on the task as its last writer. When the last writer does not change, that is the user of the environment that flushes the change: the acting user in an ordinary request, also under sudo().
  • The stage name of a row is the source-language name (en_US) of the stage when the row was written. A row From the chatter has the name the chatter tracked.
  • During an update with the server running, a worker that still runs the previous code changes stages without writing a row, and the fill does not come back to a task that has rows.
  • The fill tells a changed stage from the stage of creation by the 2 seconds between the creation of the task and its last stage update. The creation date is the start of the transaction, so a task created 2 seconds or more into a long transaction gets its row From the last stage update, without a user, though its stage never changed.
  • Of the stage changes the chatter did not track before the log existed, the filled past holds at most the stage the task is in, at its last stage update.

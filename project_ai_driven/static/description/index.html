Project AI-driven

Additions to project tasks for AI-driven development: task attributes, clarifying questions as rows with their answers, the technical solution, a checklist and test cases per task, pull requests as records, the project that develops this Odoo and the installed modules its tasks touch, the internal notes of tasks by category, and two rules on the stages a project marks: a Resolution to enter some, a task type and an estimate to enter others. The module also logs the stage changes of every task of the database.

Task attributes (project.task)

  • Priority (Highest to Lowest), Estimate, Size and Task Type (Feature, Bug, Improvement, Investigation, Milestone, Support, Technical Debt), next to the tags on the task form. The type is also a column of the task list; its tracking messages name the field AI-driven Task Type. Neither the type nor the estimate has a default value.
  • Estimate is the core field planned_hours (Initially Planned Hours), in hours. Size (tshirt_estimate) is stored, read-only and follows it: XS up to 2 hours, S up to 6, M up to 12, L up to 32, XL up to 60, XXL above; empty while the estimate is not above zero. A size sent in a write is dropped and one sent at creation is recomputed from the hours; neither call is refused. With Timesheets installed, its tab on the task shows the same field as Allocated Hours (Allocated Days where the company encodes timesheets in days).
  • The core priority star is hidden on the tasks of a project flagged AI-driven Project: on the form, the kanban card, the task list, the Sub-tasks and Blocked By lists of the form and the calendar popover. Its stored value is not touched: core still orders tasks by it, and the filters High Priority and Low Priority still search on it. The tasks of other projects keep the star.
  • A Technical Solution tab with the Questions list and the Solution, shown to project users on the tasks of a project flagged AI-driven Project.
  • Assignment notifications honour the mail_auto_subscribe_no_notify context, so an account without an email address (an RPC service account) can assign tasks without failing.

Checklist (project.task.checklist.item)

Task-level checklist items, the Checklist of the task (checklist_item_ids), each with a description, an Assigned to user, a Reviewer, a deadline and a state: TODO, Waiting, Done, Cancelled. A new item’s assignee and reviewer default to the user who creates it, on the form and over RPC; the reviewer is read-only on the form. Items have no activities.

An item is found, read, changed, deleted and created by the users who can read its task, archived or not: the record rules of the task apply to its items, the companies selected in the company switcher included. The superuser and sudo() reach every item.

Only the assignee or the reviewer of an item changes its state, description or assignee. The check runs before the write, against the assignee and the reviewer the item has then: the assignee may hand the item over and change its state in one write, another user cannot take it. The deadline, and the reviewer over RPC, are changed by anyone who can change the item.

A creation and a change of state, description or assignee make one post per item on the task, addressed to the item’s assignee and reviewer, and to its former assignee on a change of assignee, other than the user making the change, under the internal All checklist updates subtype. When no one else is left, the post is a note addressed to no one. A change of description shows the former description under the former state. A post is written in the language of the user making the change. The subtype is not subscribed by default: other followers receive the posts of others only after opting into All checklist updates on the task or on its project. The same context key silences these posts for an account without an email address.

The assignee or the reviewer of an item converts it into a sub-task of its task, whatever its state, in a project with Sub-tasks turned on, so never on a task without a project. The conversion needs the right to create a task in that project under the record rules of tasks, those other modules add included. In Odoo 16 a project visible to Invited internal users refuses it to whoever neither follows the project nor is a Project / Administrator (group project.group_project_manager), even the item’s assignee, as Odoo reads the new task before writing its assignees. The Convert to Sub-task icon and button show to a user who may convert the item under these rules; the closing and estimate rules of the first stage, below, an author without an email address, and a rule on a field Odoo computes only once the task is created can still refuse the conversion after the click.

The sub-task takes the item’s description as its title, its assignee, and the date of its deadline in the time zone of the user converting it, or no deadline. Its parent is the task, its project the task’s, its stage the first unfolded stage of that project; it takes no default of the screen the conversion starts from. The assignee and the reviewer follow it. When the reviewer converts an item assigned to another user, that user gets Odoo’s You have been assigned to notice. The task gets an internal note, without a category, linking the sub-task, and the item is deleted. The conversion also takes the right to delete the item, and when the closing or the estimate rule marks that first unfolded stage, the stage refuses the sub-task, which has no Resolution, type or estimate. Any refusal leaves the item and the task as they were, with no sub-task.

The task’s kanban card shows the current user’s completion percentage over their non-cancelled items and the number of their TODO and Waiting items. The Checklist menu opens on your own TODO items (the My and TODO filters are on by default); remove those filters to see every item you can read.

Test cases (project.task.testcase)

Ordered test cases per task with Steps to execute, Expected results and Comments. The Status of a case is its result: Not run (the default), Passed, Failed, Waiting or Not applicable.

  • Verified by and Verified on: who gave the last Passed or Failed, and when. A create or write that sets Passed or Failed fills them with the user who makes it, also under sudo(), and the current time; a value the same call gives is kept. Passed or Failed given again is a new verification. Not run clears them and Verification; Waiting and Not applicable leave them.
  • Verification: Manual, Automated test or Demo. A result button other than Not run sets it to Manual when it is empty.
  • Automated test reference: the automated test that verifies the case, such as a test selector. Not run leaves it.
  • Passed (passed) is stored, read-only and follows the status: set for Passed only.

The task carries general comments and a completion percentage: its Passed cases over all its cases but the Not applicable ones. Its kanban card counts the cases Not run, Failed and Waiting. The Test Cases menu opens filtered on the cases Not run; remove the Not run filter to see them all. Copying a task also copies its checklist items, keeping their states, and its test cases, keeping their status, Verified by, Verified on, Verification and Automated test reference.

Questions (project.task.question)

The clarifying questions of a task, its Questions (question_ids), are rows in an order of their own:

  • Round: the round of questions the row was asked in, a name or a date.
  • Question and Answer: rich text.
  • Addressed to: the internal user the question is for.
  • Status: Open, Answered or Dropped. A row is Open until it gets an answer that shows something: text, an image, a video or an icon. A create or a write that gives such an answer to an Open row makes it Answered, unless the same call sets the status; a Dropped row stays Dropped. An answer of spaces, empty paragraphs or empty list items leaves the row Open.
  • Answered by and Answered on: who made the row Answered, and when. A create or write that makes a row Answered fills them with the user who makes it, also under sudo(), and the current time; a value the same call gives is kept. A row already Answered keeps them when it is set Answered again or gets another answer. Open clears them and keeps the answer; Dropped leaves them.

A row is named by the text of its question, cut at 80 characters, or of its answer when the question is blank, or else by its task. A row is found, read, changed, deleted and created by the users who can read its task, as a checklist item is. Copying a task copies its rows with all their values, the status, Answered by and Answered on included.

Pull requests (project.pull.request)

A pull request is a record of its own, shared by every task it belongs to:

  • URL, required and unique, stored in canonical form: scheme and host in lower case, then the path as written, up to and including the number. /files, a query, a fragment or a closing slash after the number are dropped.
  • Repository and Number, read from the URL. The record is named <repository>#<number>, for example owner/repo#12, and is found by that name or by a part of its URL.
  • State: Open, Merged or Closed. A new record is Open; one created by the conversion described under Installation has no state.
  • Merge Date, Deploy Date and the Tasks it is linked to.

A pull request link is an http(s) URL with a repository path followed by /pull/N, /merge_requests/N (also /-/merge_requests/N), /pull-requests/N or /pulls/N, N being a number of at most nine digits.

Internal users read pull requests; Project / User also creates and edits them. No access right allows deleting one, and portal users have no access.

Pull requests and Resolution on a task (project.task)

  • Pull Requests (pull_request_ids): the pull requests of the task, on a tab of their own on the tasks of an AI-driven project.
  • Resolution (resolution): how the task was closed: Code, Data, Configuration or No change. It is shown on the tasks of an AI-driven project, and its changes are tracked in the chatter.
  • First Pull Request (pr_uri) reads the link of the task’s first pull request, the one created first, and is empty when the task has none. It is on no view of this module. It is stored, so it can be searched, its changes are tracked in the chatter, and it is writable for the tools that write it over RPC. Writing one pull request link finds the record with that link or creates it, and adds it to the task; a link the task already has changes nothing, and neither does an empty value. Anything that is not exactly one pull request link (other text, a link without http(s)://, a commit or branch link, two links) is refused: a task closed without a pull request takes the Resolution Data, Configuration or No change instead.
  • PR (old value) (pr_legacy), read-only: the whole text pr_uri held before the conversion described under Installation, where that text was anything but one plain pull request link.
  • A duplicated task starts without pull requests, Resolution and old value. A copy that keeps the stage of its source, as every task and subtask of a duplicated project does, takes the Resolution and the pull requests of its source.

The closing rule

On an AI-driven project, Stages Requiring a Resolution (pr_required_states) marks stages. A task of that project enters a marked stage only with a Resolution:

Resolution Pull request Result
empty none refused: choose a Resolution
empty present let through, Resolution = Code
Code none refused: add a pull request
Code present let through
Data, Configuration, No change none let through
Data, Configuration, No change present let through, pull request kept

The rule is checked when the stage of the task changes: on creation, on a write of the stage and on a change of project that moves the task to another stage. The Resolution and the pull request may come in the same write as the stage. Any other stage, a project that is not flagged AI-driven and a write that leaves the stage as it is let everything through, so a task already sitting in a marked stage stays editable. No context key skips the rule.

The estimate rule

On an AI-driven project, Stages Requiring a Type and an Estimate (estimate_required_states) marks stages. A task of that project enters a marked stage only with a Task Type and an Estimate above zero hours. The refusal names what is missing, the type, the estimate or both, each with the tasks that lack it.

The rule is checked where the closing rule is: on creation, on a write of the stage and on a change of project that moves the task to another stage. The type and the estimate may come in the same write as the stage, and a task created straight into a marked stage needs both in the values of its creation. Any other stage, a project that is not flagged AI-driven and a write that leaves the stage as it is let everything through, so a task already sitting in a marked stage stays editable. No context key skips the rule. A stage marked for both rules refuses for the Resolution first.

The next task of a recurrence takes the task type of the last one, as it takes its estimate.

The project that develops this Odoo (project.project)

  • Develops This Odoo (develops_this_odoo) marks the AI-driven project whose tasks change the Odoo database the module runs in. One project of the database carries it at most, archived projects included: a second one is refused, and the refusal names the project that has it, also to a user who cannot read that project. Ticking it on a project that is not AI-driven, or clearing AI-driven Project on the project that has it, is refused.
  • Only a Settings administrator (Administration / Settings) sets or clears it, at creation (a context default included) or in a write; a write that leaves it as it is passes for any user. Only a Settings administrator archives or deletes the project that carries it.
  • The project form shows it to Settings administrators, below AI-driven Project, on a project that is AI-driven or carries it. A change is tracked in the chatter of the project. A duplicated project starts without it.
  • The task has the same field, related to its project, read-only and readable by every user who reads the task.

Modules of a task (project.task)

  • Modules (module_ids): the installed modules the task touches, records of the module list (ir.module.module). On the tasks of the project that develops this Odoo the form shows them after the Resolution, as tags bearing their technical names, and offers only installed modules. On the tasks of other projects the form hides them; they are kept, and the project does not stop a create or a write of them. A duplicated task starts without modules.
  • A create or a write refuses a module it adds that is not installed; To be upgraded and To be removed count as installed, To be installed does not. The refusal names the modules, and the whole call is refused. A module already on a task stays there when it is uninstalled: the task saves with it, and a write that keeps it or links it again to that task passes.
  • Module Names (module_names), not stored and on no view: the technical names of the modules, sorted, separated by ", "; False without modules.
  • The task search has a Module field: it finds tasks by a module’s technical name or title.
  • Both fields, and the Module search, are for Project / User only. Project users read the module list, by an access right of this module.
  • Under the context key module_technical_name a module is named by its technical name instead of its title. The picker passes it, with a list and cards of the technical name and the title, without buttons; the Apps menu keeps the views of base.

The stage log (project.task.stage.log)

One row when a task is created with a stage and one row on every change of its stored stage, for every task of the database, in an AI-driven project or not. The rows are written by SQL where the row of the task is written, so no context (tracking_disable, mail_notrack, mail_create_nolog) and no sudo() goes around the log, and a stage recomputed by a change of project is logged too, on the task and on the subtasks moved with it.

  • Task, Date and User: the task, when its stage changed and who changed it. The user is empty when it is not known. Deleting a task deletes its rows.
  • Stage and Stage Name: the stage the task entered. The stage is empty when the task left its stage, and when the stage was deleted since; a deleted stage keeps its name.
  • Previous Stage: the stage the task left. It is empty when there was none, when it is not known and when it was deleted since.
  • Source: Recorded for a row written with the change; From the chatter, From the last stage update or From the creation date for a row of the past, filled as described under Installation.

A task created without a stage gets no row. A task that loses its stage gets a row with an empty stage. A write that carries the stage the task already has writes no row.

Only system administrators read the log, and no access right allows creating, changing or deleting a row. The log has no view and no menu. A search of the log first flushes the stage changes that are pending.

Task notes (mail.message)

  • Task (task_id): the task a message is posted on, empty for a message of another model and for one whose task no longer exists. It is stored, set from the model and the record of the message, and emptied when the task is deleted.
  • Category (note_category): Requirement Change, Design Decision, Bug Fix, Review Fix, User Feedback, Progress, Revised or Deploy, given to an internal note of a task whose body opens with it in bold. It is stored, and read again when the body, the record or the subtype of the message changes, as when a note is edited.
  • is_task_readable, not stored: whether the current user, in the companies they selected, can read the task of the message, archived tasks included. It is searched as SQL, with = or != and a boolean (True / False or 1 / 0), so that a page of a list holds only messages of readable tasks.

The category of a note:

  • An internal note is a message of the Note subtype, of any message type. A message to the followers, a message on another model and a message that tracks changed fields get no category, whatever their body.
  • The body opens with the bold text (<b> or <strong>): only white space, &nbsp; and at most one opening tag, <p> or <span>, with or without attributes, come before it.
  • The bold text opens with the category, in any letter case, and ends there or goes on after a dash, a colon, a slash, a plus or an opening parenthesis: <b>Bug Fix</b>: the total, <b>Progress: 2/2</b>, <b>Bug Fix (round 2)</b>. Bold text naming two categories gets the first. <b>Progress report</b> and <b>Deploy notes</b> get none.

Odoo lets only administrators group messages. A project user also groups them on a domain that filters on is_task_readable, as the Task Notes list does: the groups and their counts hold only messages of tasks the user can read, and a group opens on the user’s own domain with the condition of the group. The group-by fields are category, task, author, date, model, message type and subtype; any other group-by, and any other grouped read of messages, stays refused to users who are not administrators.

Installation

A database that has installed neither project_software nor the project-specific module it was cut from needs nothing beyond installing the module. What a database that has project_task_pull_request installed needs on top of that is under Coming from project_task_pull_request. What the install and the update to 16.0.2.2.0 write to the stage log for the tasks that exist is under Filling the stage log.

The update to 16.0.2.3.0 deletes the fields difficulty, knowledge_area_level and tester_id of project.task with their columns and the values in them; the install that takes over project_software or the project-specific module it was cut from deletes them too. Beforehand the three fields are taken out of the stored views of this module; a view outside this module that names one of them is not rewritten: change it by hand.

The update to 16.0.2.4.0 sets the Size (tshirt_estimate) of every task, archived tasks included, to the size of its hours (planned_hours); the install that takes over project_software or the project-specific module it was cut from does it too. One SQL statement stores the sizes and writes nothing else on the tasks: the task type, the hours and the last update date stay as they are. A task without hours ends with no size, and a size that disagrees with the hours of its task is replaced by theirs; the former value is not kept. The server log gets one line with the number of tasks changed; a second run changes none. On a database that has neither module installed, the install computes the size of the tasks that exist through the ORM, which writes those tasks.

The update to 16.0.2.4.1 sets to zero the hours (planned_hours) of every task that holds a NaN or an infinity, archived tasks included, and recomputes what is computed from them: the size, none for zero hours, and with hr_timesheet the remaining hours. From this version a write refuses such hours, so a task holding them could no longer be copied or recur. No tracking message is posted; the recompute stamps the last update date of those tasks. The server log gets the number of tasks changed. The install does the same.

The update to 16.0.2.5.0 converts the Status of every test case: TODO becomes Not run, Done Passed, Cancelled Not applicable, and Waiting stays. Passed (passed) is then set from the status wherever it disagrees: set for Passed, cleared for any other status. The install that takes over project_software or the project-specific module it was cut from does it too. SQL statements store the values and write nothing else on the cases: the last update date stays, and Verified by, Verified on and Verification stay empty on a converted case. The server log gets the number of cases converted per former value and of flags corrected; a second run changes none. Odoo deletes the former values of the selection at the end of the update. A saved filter, a default or a server action that names a former value is not rewritten: change it by hand.

Beforehand the buttons of the former states (change_state_*) are taken out of the test case list of the stored task form of this module, in every translation; the update and the install that takes over would otherwise fail validating the task form. A view outside this module that names one of them is not rewritten: change it by hand.

The update to 16.0.2.6.0 renames the checklist model project.task.subtask to project.task.checklist.item, its table to project_task_checklist_item, and the task fields subtask_ids and kanban_subtasks to checklist_item_ids and kanban_checklist. The task field default_user is deleted. The former names are not kept: a client that names the former model gets Object project.task.subtask doesn’t exist.   • the external ids of the model, its fields and their selection values;
  • as whole words, the fields in the stored arch of the views of the checklist and of the models holding the fields, in every translation, and the fields and the model in record rule domains, filters and window actions;
  • the file recorded on the views loaded from the renamed view file.

The update to 16.0.2.7.0 turns the questions and answers of every task, archived tasks included, from the Html fields questions and answers of the task into question rows. The install that takes over project_software or the project-specific module it was cut from does it too. Html that shows no text, image, video, embedded frame or icon is blank. Lists alone is Html of top-level numbered or bulleted lists, each after at most one block of text, its heading, with nothing else: no other text, no image, video, embedded frame, icon or list in a heading, no list inside another block. The heading gives the round of the rows of its list, as plain text. A list nested in a list belongs to the item before it; a list nested before any item makes the Html something else.

Questions and answers Rows
both lists alone, as many lists on each side, as many items in each pair of lists a row per pair of items, Answered, or Open where the answer item is blank; a pair of two blank items gives no row. The task is kept whole where a heading would be in no row: when the items of a pair of lists with a heading are all blank (every pair blank, too), or the answers under a heading other than the round of their questions are all blank
anything else on both sides one row of both as they are, Answered
questions alone, lists alone a row per item that is not blank, Open; one row of the questions as they are when the items of a list with a heading are all blank (every item blank, too), so that no heading is lost
questions alone, anything else one row of the questions as they are, Open
answers alone one row of the answers as they are, without a question, Answered
both blank none

Where an answer list has a heading other than the round of its questions, the heading is put in front of each of its answers, so that a name or a date it gives stays with them. Names and dates in the answers are not read: a converted row has no Answered by and no Answered on. SQL inserts the rows, in the order of the Html, as the superuser, and writes nothing on the tasks. A task that already has rows is skipped, so a second run inserts nothing. The server log gets one line with the number of tasks of each case and of rows inserted per status.

Before the data files are loaded, the two fields are taken out of the stored views of this module, in every translation; the update would otherwise fail validating the task form. A view outside this module that names one of them is not rewritten: change it by hand.

This module does not declare the two fields. At its end the update deletes them with their columns, unless a module updated in the same run declares them: that module keeps the fields and their columns. Without them, the content is in the rows only. An update that finds the columns missing logs a warning and converts nothing.

The update to 16.0.2.8.0 gives every message of a task its Task (task_id), archived tasks included, and every internal note of a task its Category (note_category); the install does the same. Before Odoo sets up the fields, SQL creates their two columns in mail_message where they are missing, with the partial indexes Odoo looks for, so that Odoo computes neither field over the messages of the database. SQL then fills the columns by the rule of the fields, clears any value a message should not hold, and writes nothing else on the messages. The two columns are analyzed last, so that the query planner has their statistics from the start. The server log gets one line with the number of messages given a task and cleared, and of notes given each category and cleared; a second run changes nothing.

Odoo then adds the foreign key of task_id, which reads the message table once. Making the columns and the key locks the message table until the module is loaded, and a running server waits on it meanwhile: on a large database, run the update or the install with the server stopped.

The update to 16.0.2.8.1 gives their Category to the internal notes of tasks that have none and whose body opens with a <span>, by SQL over those notes alone. It adds no column and writes nothing else on the messages. The server log gets one line with the number of notes given a category; a second run changes nothing.

The update to 16.0.2.9.0 adds the Modules of a task: it creates the table project_task_ir_module_module_rel, the two views of the module picker, the Module field of the task search and an access right that lets Project / User read the module list. The update to 16.0.2.10.0 adds Develops This Odoo to projects, with its column, and the same field on tasks, related to the project and not stored. Upgrading from project_software

project_software remains for one release as an empty module that depends on this one, so updating it installs this module. Before any data file is loaded, the pre_init_hook takes over everything project_software owns: models, fields, views, access rights, menus and message subtypes keep their database ids, so checklist items, test cases, field values and follower subscriptions stay as they are. It renames the flag where the database stores it: the column, the field on every model that has it, and the view archs, record rule domains, filters and window actions that name it.

What the upgrade needs:

  • addons.yaml lists both modules for that release, also when it pins a commit.
  • The deploy runs an update of project_software (-u project_software) with the server stopped: the hook renames the flag’s column, which running code still reads. A restart without the update leaves project_software and the modules that depend on it unloaded.
  • A module that depends on project_software switches, in the same deploy, its dependency and its external id references to project_ai_driven and the flag to is_ai_driven. The hook rewrites its stored views; data files with the former name would write it back. The view project_project_view_form_inherit_software is now project_project_view_form_inherit_ai_driven.
  • Text naming the flag elsewhere (server action code, automated action domains, export templates) is not rewritten: change it by hand.
  • project_software is uninstalled, once no installed module depends on it, before the release that removes it, and dropped from addons.yaml.

A dependent module that is renamed as well can call three functions of odoo.addons.project_ai_driven.hooks from its own pre_init_hook:

  • is_installed(cr, module_name): whether a module is installed or marked for upgrade.
  • take_over_module(cr, former, module): moves to module everything former owns: external ids, constraints, many2many tables and the views loaded from its files. The caller clears the registry caches.
  • rename_external_ids(cr, module, renamed_names): renames external ids of module from a {former name: new name} dict.

Upgrading from the module it was cut from

On a database from before the features were cut from the project-specific module, where project_software was never installed, the hook takes over only what moved here and renames the flag the same way.

Coming from project_task_pull_request

This module declares pr_uri on the task and pr_required_states on the project and the task under the names, the column and the relation table of OCA project_task_pull_request, and takes its place. The stages marked on each project stay marked, the tracking history of pr_uri stays on the field, and whatever reads pr_uri or writes a pull request link to it keeps working. pr_uri takes one pull request link and no other text: a tool that writes a note there for a task without a pull request sets resolution instead.

The text project_task_pull_request stored in pr_uri is converted when this module is updated to 16.0.2.1.0 (migration script) or installed (post_init_hook):

Old value Becomes
one pull request link, whatever the case of its scheme and host, with or without spaces around it and a closing slash a pull request on the task, Resolution Code
several pull request links one pull request per link, Resolution Code, old value kept
a pull request link without https:// a pull request with https:// added, Resolution Code, old value kept
a pull request link with more after the number (/files, a commit, words) or an invisible character before it the pull request itself, Resolution Code, old value kept
a link that is not a pull request link (commit, branch, repository, another site, no repository before /pull/N, a number of more than nine digits) no pull request, old value kept
a memory:// reference or any other text no pull request, old value kept
empty nothing

Old value kept means the whole text is in PR (old value) (pr_legacy). Nothing is guessed: a pull request created by the conversion has no state, one that already exists is linked as it is, and the Resolution is set to Code only where it is empty. The same link on several tasks gives one pull request. Afterwards pr_uri reads the task’s first pull request, or is empty. Archived tasks are converted too. The tasks are written by SQL, so their last update date does not change, no tracking message is posted and no constraint runs. The log of the update gives the number of values of each kind; a second run converts nothing.

This module does not depend on project_task_pull_request and does not uninstall it. A module that depended on it, or an administrator, uninstalls it once this version is installed, not before: the fields and the relation table stay only because this module declares them too. While it is installed, its constraint requires a non-empty pr_uri in the marked stages of every project, AI-driven or not, so a task without a pull request cannot enter them, whatever its Resolution.

Its code leaves the addons path in the deploy that uninstalls it. While the code is there, the labels stored for the shared fields are its own, PR URI and PR Required States, and they stay until the first update after it is gone.

Filling the stage log

The tasks that exist get the past of their stages in the stage log when this module is updated to 16.0.2.2.0 (migration script) or installed (post_init_hook). One SQL statement inserts the rows of every task that has none, archived tasks included, and writes nothing on the tasks:

Task Rows
with stage changes of its own in the chatter the stage it was created in, then one row per tracked change, all From the chatter
the same, when the last tracked change does not end at the stage the task is in one more row: that stage, empty for a task that is in none, at the last stage update, without a user, From the last stage update
in a stage, without such changes, last stage update 2 seconds or more after its creation one row at the last stage update, without a user, From the last stage update
in a stage, without such changes, otherwise one row at its creation, by its creator, From the creation date
without a stage and without such changes nothing

The stage a task was created in is the old value of its first tracked change, when that is a stage. Its row is dated at the creation of the task, or at that first change when it is dated earlier, and its user is the creator of the task. A tracked change keeps the date of its message and the stage names the chatter tracked; its user is the user of the author of the message, the one with the lowest id when the author has several, none when the author has no user. The stage changes of a predecessor, which Odoo posts on the dependent tasks, are not changes of the task and are left out.

Nothing is guessed. A tracked change that does not start where the one before ended stays as tracked. The row for the current stage is left out when the last stage update is missing or earlier than the last tracked change, and so is any row that would have no date. The fill writes one line to the server log with the number of rows of each case and of the rows left out; a second run inserts nothing.

Run the update with the server stopped. A worker that still runs the previous code changes stages without writing a row, and the fill skips a task that has rows, so such a change stays out of the log.

Configuration

  • On a project, tick AI-driven Project (Settings tab, above Visibility) to show the Technical Solution and Pull Requests tabs and the Resolution on its tasks, and to hide the core priority star on them.
  • Below it, a Settings administrator ticks Develops This Odoo on the one AI-driven project whose tasks change this Odoo database: its tasks show their Modules. The field is shown to Administration / Settings only, on a project that is AI-driven or carries the flag. One project carries it at most, archived projects included: to move it, clear it on the project that has it, then tick it on the other one. Only a Settings administrator archives or deletes the project that carries it.
  • Then, on an AI-driven project, Stages Requiring a Resolution lists the stages a task enters only with a Resolution, and with a pull request when the Resolution is Code. Only stages of the project can be picked. Leave it empty to switch the closing rule off.
  • Below that, Stages Requiring a Type and an Estimate lists the stages a task enters only with a task type and an estimate above zero hours. Only stages of the project can be picked. Leave it empty to switch the estimate rule off.
  • What creates a task straight into a stage of that second list without both values is refused there: the kanban quick create, which takes a title and assignees; an email to the alias of the project, which gives neither value; a sales order line that creates a task, which gives no task type. The duplicate of a project copies each task with its type and its estimate, so it is refused only where a task sits in such a stage without them.
  • Checklist items, question rows and test cases are managed by Project / User, a checklist item and a question row only by a user who can read its task. The Checklist, Test Cases and Technical Solution tabs are hidden from users without that group.
  • Pull requests are read by every internal user and created and edited by Project / User. No access right allows deleting one.
  • The Modules of a task, on the form and in the task search, are shown to Project / User only.
  • The stage log is read by Administration / Settings only. No access right allows creating, changing or deleting a row.
  • Project > Task Notes and the Notes button of the task form are shown to Project / User. A project user lists and groups there the notes of the tasks they can read, by category, task, author, date, model, message type or subtype; Odoo lets only administrators group other messages, or group by any other field.
  • To be notified of checklist items of which you are neither the assignee nor the reviewer, edit your follower subscription on the task or on the project and tick All checklist updates.
  • An integration that writes tasks or checklist items with an account that has no email address passes mail_auto_subscribe_no_notify in the context; without it Odoo refuses to send the notification and the write fails.

Usage

On the task form:

  • Set Priority, Estimate (in hours) and Task Type next to the tags. Size shows the size of the estimate and cannot be edited.
  • Checklist tab: add items, each with an Assigned to user, yourself unless you pick another, and an optional deadline. You are the reviewer of the items you add. A new task or sub-task, from the dialog of its parent’s Sub-tasks tab too, saves with the items added before its first save: they are created right after the task, as items added to it once saved. The assignee or the reviewer moves an item with the state icons (TODO, Waiting, Done, Cancelled), changes its description or gives it another assignee. The task’s kanban card shows your own completion percentage, only when you have non-cancelled items assigned to you.
  • Checklist tab, in a project with Sub-tasks turned on: the assignee or the reviewer converts an item into a sub-task with the level-down icon of its row, after a confirmation, if they may create a task in the project; in a project of invited internal users, only if they follow the project or are a Project / Administrator. The item is deleted and the task gets a note linking the sub-task.
  • Test Cases tab: add ordered cases with steps and expected results, then give each case its result with the icons of its row; a row offers the states other than its own (Passed, Failed, Not run, Waiting, Not applicable). Verified by and Verified on show who gave the last Passed or Failed. On a phone the tab shows cards with the same buttons. Set Verification to Automated test or Demo, and the Automated test reference, on the form of the case.
  • Technical Solution tab (AI-driven projects): the Questions list, then the Solution. Add a row per question, with its round and the user it is addressed to, and drag the rows into order. Give a row its answer and it becomes Answered, stamped with your name and the time; the status of a new row follows its answer. Once the row is saved, set it back to Open to ask again, or to Dropped when it no longer applies. The Answer column is hidden in the list until you show it. On a phone the list shows cards.
  • Pull Requests tab (AI-driven projects): add the pull requests of the task, each with its link, state, merge date and deploy date. A pull request already recorded for another task is picked from the list instead of being created again. PR (old value) shows above the list on a task that has one.
  • Resolution (AI-driven projects), next to the tags: choose it before moving the task to a stage that requires one. Code needs a pull request on the task; a task that already has one gets Code by itself.
  • Modules (the project that develops this Odoo, project users), after the Resolution: the installed modules the task touches, as tags bearing their technical names. Type a technical name or a title to pick one; only installed modules are offered, and Search More… lists them by technical name and title, cards on a phone. A module that is not installed is refused, and the refusal names it. A module uninstalled after it was added stays on the task, which still saves with it. Search tasks by Module, with a technical name or a title.
  • Task Type and Estimate (AI-driven projects): set both before moving the task to a stage that requires them. The refusal names what is missing.

Project > Checklist lists the checklist items of the tasks you can read in the selected companies, opened on your own TODO items. Group by project, task, user or status. Convert to Sub-task, in the header of an item’s form, converts it as the icon of its row does, then opens the sub-task in place of the breadcrumbs.

Project > Test Cases lists the test cases of all tasks, opened on the ones Not run: a list, cards on a phone. Filter on Not run or Failed, group by project, task, status or verification. The header of a case’s form gives it its result with the same buttons, next to its status bar: Not run, Passed and Failed, and the status of the case when it is another.

Project > Pull Requests lists the pull requests of all tasks, the newest first: a list, cards on a phone. Search by URL, repository or task, filter on Open, Merged, Closed or No State, group by repository or state. On the form of a pull request, set State, Merge Date and Deploy Date when it is merged and deployed.

Project > Task Notes lists the internal notes of the tasks you can read, archived tasks included, the newest first: a list, cards on a phone. A note of files alone is listed; a message to one user and a change of tracked fields without a note are not. Filter on a category, search by contents, task or author, and group by category or by task: a task’s group bears its current name, and the categories come in the order of the filters, the notes without one last. A note opens read-only with its files, and Open Task opens its task. Nothing is created, changed or deleted from this menu.

On the task form, the Notes button counts the notes of the task and opens them in the same list. It shows once the task has a note.

To give a note a category, log it on the task with the category in bold as its first words, alone in the bold or followed there by a dash, a colon, a slash, a plus or an opening parenthesis: Design Decision - keep the flow; Progress: 2/3.

A tool that writes over RPC sets pr_uri on the task to the link of the pull request, one link per write, or resolution to data, configuration or no_change when there is none. A write of another link adds a second pull request to the task. The estimate is written to planned_hours and the type to task_type; a tshirt_estimate sent with them is ignored. The estimate is a finite number: a NaN or an infinity is refused, in any project.

A tool that records the modules of a task over RPC, as a project user, first reads develops_this_odoo on the task and goes on only when it is True: on a task of any other project the form hides the modules, but its project does not stop a write of them. It finds their ids with search_read on ir.module.module, the domain [("name", "in", <technical names>), ("state", "in", ["installed", "to upgrade", "to remove"])] and the field name, then writes module_ids on the task with one (4, <module id>) command per module: the modules already on the task stay as they are. A write that adds a module that is not installed is refused as a whole. It reads the technical names from module_names: sorted, separated by ", ", False when the task has no module.

A tool that keeps a checklist over RPC creates project.task.checklist.item records with task_id, name and user_id, which defaults to the tool’s own user, and reads the items of a task from checklist_item_ids. Items sent with Command.create in the checklist_item_ids of a task being created are created right after the task, with the access rights of the calling user: a portal collaborator gets an access error. It moves an item by writing state (todo, waiting, done or cancelled) as the item’s assignee or reviewer. It reaches only the items of the tasks its user can read; without allowed_company_ids in the context, those of all the user’s companies.

It converts items into sub-tasks with action_convert_to_subtask, each into a sub-task of its own task, as the assignee or the reviewer of every item who may create a task in its project under the record rules of tasks: a refusal of one leaves them all. can_convert tells whether its user may convert an item under these rules; the closing and estimate rules of the first stage, the email address the note needs and a rule on a field Odoo computes only once the task is created are checked by the conversion only. The method returns True. action_convert_to_subtask_open converts one item and returns the window action of its sub-task, the id in res_id. The note on the task is posted in the name of the tool’s user, who needs an email address even with mail_auto_subscribe_no_notify; that key silences the assignee’s notice.

A tool that keeps the questions of a task over RPC creates project.task.question records with task_id and question, and round, addressed_to_id and answer when it has them, and reads the rows of a task from question_ids. It answers a row by writing answer; state takes open, answered or dropped. A create or write that makes a row Answered fills answered_by_id and answered_on unless it sends them. It reaches only the rows of the tasks its user can read.

A tool that gives test case results over RPC writes state on project.task.testcase: not_run, passed, failed, waiting or not_applicable. A create or write of passed or failed fills verified_by_id and verified_on unless it sends them. It sends verification_kind (manual, automated or demo) and test_reference with the result: only the buttons set manual by themselves. The former values todo, done and cancelled are taken as not_run, passed and not_applicable. passed is read, not written: a value sent for it is dropped, and passed true without a state gives passed.

A tool reads the notes of one category of a task with search_read on mail.message, the domain [("task_id", "=", <task id>), ("note_category", "=", "design_decision")] and fields such as date, author_id and body. note_category takes requirement_change, design_decision, bug_fix, review_fix, user_feedback, progress, revised or deploy. It reaches the messages its user can read. It gives a note a category by posting it on the task with message_post, subtype_xmlid mail.mt_note and a body that opens with the category in bold, in a paragraph: <p><b>Progress</b> - in review</p>. A body of more than one node that opens with an inline tag and holds no block tag, such as <b>Progress</b> - in review, is stored inside a <span> and gets its category too. A grouped read (read_group) of messages takes a project user, ("is_task_readable", "=", True) in the domain and group-bys among note_category, task_id, author_id, date, model, message_type and subtype_id.

The stage log has no view and no menu. A system administrator reads project.task.stage.log over RPC: the rows come ordered by date, each with task_id, previous_stage_id, stage_id, stage_name, date, user_id and source (live, tracking, stage_date or creation). The log holds the stages of every task, so code that shows it to other users reads it with sudo(), for the tasks those users can read.

Known issues / Roadmap

  • This module does not keep the former Html questions and answers of the task: without another module that declares them, the update to 16.0.2.7.0 deletes them with their columns, and their content is in the question rows only.
  • The conversion pairs list items by position: two lists of as many items pair the first question with the first answer, also where an answer was written for another question.
  • A row kept whole holds every question and answer of its task: split it by hand.
  • The round of a converted row is the text of a heading, without its formatting.
  • Question rows have no chatter: a change of status or answer leaves no trace but Answered by and Answered on.
  • The test case flag passed and the translation of the former state values (todo, done, cancelled) at create and write serve clients written for the former selection, until a later version removes them.
  • The path of a pull request link is stored as written. Two spellings of one pull request (Owner/Repo and owner/repo, http and https, with and without /-/) are two records.
  • Nothing reads a pull request from its host: State, Merge Date and Deploy Date are set by hand or over RPC.
  • The pull requests of a task are tracked only through pr_uri: one that is added without becoming the task’s first leaves no trace in the chatter. Odoo 16 tracks no many2many field.
  • A change of the Modules of a task leaves no trace in the chatter, for the same reason.
  • A module that a pull request of the task brings into the code base is added to the task only once it is installed in the database.
  • Deleting a module from the module list, which Odoo refuses for a module installed or about to be, takes it off every task that held it.
  • The closing rule and the estimate rule are checked on the tasks of a write that names their stage or their project. A stage recomputed for another reason is not checked, as for a subtask whose parent changes project, and neither are the other tasks of a recurrence that the write is extended to.
  • A module that writes a task’s new project on its own, before the other values of the same write, runs both rules before the Resolution, the task type and the estimate of that write arrive. Setting them in an earlier write avoids it.
  • Neither rule is run when a stage gets marked or a project gets flagged, so a task can sit in a marked stage without what the stage requires: a Resolution, a pull request, a task type or an estimate. Such a task stops the duplication of its project until it gets it.
  • The priority star is hidden on the views the description lists. The portal keeps it: the project sharing views, the task list and the task page.
  • A row of the stage log is written when the change of stage is flushed to the database. Several changes of a task’s stage within one flush are one row, from the stored stage to the last one, and a change undone within one flush leaves none.
  • A stage written by raw SQL is not logged.
  • The user of a recorded row is the one the update leaves on the task as its last writer. When the last writer does not change, that is the user of the environment that flushes the change: the acting user in an ordinary request, also under sudo().
  • The stage name of a row is the source-language name (en_US) of the stage when the row was written. A row From the chatter has the name the chatter tracked.
  • During an update with the server running, a worker that still runs the previous code changes stages without writing a row, and the fill does not come back to a task that has rows.
  • The fill tells a changed stage from the stage of creation by the 2 seconds between the creation of the task and its last stage update. The creation date is the start of the transaction, so a task created 2 seconds or more into a long transaction gets its row From the last stage update, without a user, though its stage never changed.
  • Of the stage changes the chatter did not track before the log existed, the filled past holds at most the stage the task is in, at its last stage update.
  • The breadcrumb of a note opened from Task Notes shows the name its task had when the note was posted; the title of the note, the list and the groups show the current name of the task.
  • A note whose category is in bold inside a heading or a list, or coloured, gets no category: only one opening <p> or <span> may come before the bold, and nothing between the bold and the category.
  • The eight categories and their spelling are fixed in the module: Bugfix or Deployment in bold is no category.

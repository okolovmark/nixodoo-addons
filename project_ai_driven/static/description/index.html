Project AI-driven

Additions to project tasks for AI-driven development: task attributes, clarifying questions as rows with their answers, the technical solution, a checklist and test cases per task, pull requests as records, the agent sessions that worked on a task, the project that develops this Odoo and the installed modules its tasks touch, the internal notes of tasks by category, and two rules on the stages a project marks: a Resolution to enter some, a task type and an estimate to enter others. The module also logs the stage changes of every task of the database, keeps the images of the texts of every task, question row and test case as attachments of the record holding the text, and gives every task a brief: the whole task in Markdown, in one read. Projects and their tasks get keys, such as PROJ-12, that name them and open them by link.

Task attributes (project.task)

  • Priority (Highest to Lowest), Estimate, Size and Task Type (Feature, Bug, Improvement, Investigation, Milestone, Support, Technical Debt), next to the tags on the task form. The type is also a column of the task list; its tracking messages name the field AI-driven Task Type. Neither the type nor the estimate has a default value.
  • Estimate is the core field allocated_hours (Allocated Time), in hours. Size (tshirt_estimate) is stored, read-only and follows it: XS up to 2 hours, S up to 6, M up to 12, L up to 32, XL up to 60, XXL above; empty while the estimate is not above zero. A size sent in a write is dropped and one sent at creation is recomputed from the hours; neither call is refused, but for a portal user, whose create or write sending a size core refuses, as for any field outside the portal’s writable fields. With Task Logs (hr_timesheet) installed, timesheet users also see the same field as Allocated Time on the tasks of a project that uses timesheets.
  • UAT users (uat_user_ids): the users who run the acceptance tests of the task, after the Assignees on the form of every task, picked as the Assignees are among the active internal users of the task’s company; an archived one stays shown. Changes are tracked. No copy takes them: a Duplicate, a task created from a template and the tasks of a duplicated project start without UAT users.
  • The core priority star is hidden on the tasks of a project flagged AI-driven Project: on the form, its Sub-tasks and Blocked By lists, the kanban card, the task list and the calendar popover. Its stored value is not touched: core still orders tasks by it, and the Priority filters of the search still search on it. The tasks of other projects keep the star, also in the same list. The task list of a flagged project opened from the project has no Priority column at all.
  • A Technical Solution tab with the Questions list and the Solution, shown to project users on the tasks of a project flagged AI-driven Project.

Checklist (project.task.checklist.item)

Task-level checklist items, the Checklist of the task (checklist_item_ids), each with a description, an Assigned to user, a Reviewer, a deadline and a state: TODO, Waiting, Done, Cancelled. A new item’s assignee and reviewer default to the user who creates it, on the form and over RPC; the reviewer is read-only on the form. Items have no activities.

An item is found and read by the users who can read its task, and created, changed and deleted by the users who can change the task, archived or not. Its two access rights carry the domains [('task_id', 'access', 'read')] and [('task_id', 'access', 'write')], so the record rules of the task apply to its items, the companies selected in the company switcher included. Moving an item to another task also takes write access to that task. The superuser and sudo() reach every item. Reading, changing or deleting an item deleted meanwhile raises MissingError, as core does.

Only the assignee or the reviewer of an item changes its state, description or assignee. The check runs before the write, against the assignee and the reviewer the item has then: the assignee may hand the item over and change its state in one write, another user cannot take it. The deadline, and the reviewer over RPC, are changed by anyone who can change the item.

A creation and a change of state, description or assignee make one post per item on the task, addressed to the item’s assignee and reviewer, and to its former assignee on a change of assignee, other than the user making the change, under the internal All checklist updates subtype. When no one else is left, the post is a note addressed to no one. A change of description shows the former description under the former state. A post is written in the language of the user making the change. The subtype is not subscribed by default: other followers receive the posts of others only after opting into All checklist updates on the task or on its project. The mail_auto_subscribe_no_notify context key silences these posts, the way it silences the assignment notification of a task in Odoo itself: an integration writes tasks and checklist items with it and nobody is notified.

The items a new task is created with, as Command.create in its checklist_item_ids (a sub-task created from its parent included), are created right after the task, in their order, as items added to a saved task: their posts come after the creation message of the task, and the followers of All checklist updates on its project receive them. They are created with the access rights of the caller and without the default_* keys of the context, which are the task’s.

The task’s kanban card shows the current user’s completion percentage over their non-cancelled items and the number of their TODO and Waiting items. Only users with the User access of Project read these figures, the task fields completion, completion_xml and kanban_checklist, and see them on the card; an internal user without that access reads every other field of the task. These figures, the buttons of an item and the red of one’s own TODO items are computed for the user who reads them, also where two users read the same task in one transaction. The Checklist menu opens on your own TODO items (the My and TODO filters are on by default); remove those filters to see every item you can read.

An item that turns out to be work of its own is converted into a sub-task of its task (action_convert_to_subtask):

  • Only its assignee or its reviewer converts it, as for a change of its state, and only where they may change the task: deleting the item takes it. Its reviewer also needs to read the task’s project, or to be a project manager: Odoo 20 lets a project user create a task only in a project they may read or as one of its assignees, and the sub-task goes to the item’s assignee. Following the task does not count: the sub-task gets its followers, its creator and those of the task, only once it is created. So a reviewer assigned to a task of a project open to its team members only, without being one of them, changes the task but does not convert its items. The Convert to Sub-task buttons show only to who may convert under these conditions, those of templates and private tasks below included, computed for the user and for the companies selected in the company switcher: an item of a task of a company left out of the selection shows none.
  • The sub-task takes the item’s description as its title, its assignee and its deadline, and the project of the task, so also the company of that project when the user has several selected. It is given no stage: core puts it in the first unfolded stage of the project by sequence. No default of the calling view reaches it.
  • The item’s reviewer follows the sub-task, next to the followers core gives it. Core notifies the assignee of the sub-task unless the assignee converts the item; mail_auto_subscribe_no_notify silences that, as for any task.
  • An internal note on the task, by the user converting, links the sub-task. It opens with plain text, so it gets no category, and names the item by its description as text: markup in it shows as written. The item is deleted.
  • An item of a task template becomes a template sub-task: in the template’s project and its first stage, or without project and stage, then only by its assignee or by a project manager who is its reviewer. An item of a private task is refused, since Odoo 20 gives a private task no sub-task.
  • A refusal, of the user, of a private task, of a task the user may not change, of a reviewer who may not create the sub-task or of a first stage that refuses the new sub-task under the closing rule or the estimate rule, leaves the item as it was, without sub-task or note.

Test cases (project.task.testcase)

Ordered test cases per task with Steps to execute, Expected results and Comments. The Status of a case is its result: Not run (the default), Passed, Failed, Waiting or Not applicable.

  • Verified by and Verified on: who gave the last Passed or Failed, and when. A create or write that sets Passed or Failed fills them with the user who makes it, also under sudo(), and the current time; a value the same call gives is kept. A case created Passed or Failed by a default, of the context or of ir.default, is filled the same way. Passed or Failed given again is a new verification. A create or write that gives Not run clears them and Verification, also a value the same call gives; Waiting and Not applicable leave them.
  • Verification: Manual, Automated test or Demo. A result button other than Not run sets it to Manual when it is empty. A case prepared for its run keeps the Verification it is given: a case created without a Status, or a Not run case given a Verification alone.
  • Automated test reference: the automated test that verifies the case, such as a test selector. Not run leaves it.

A case follows the access of its task as a checklist item does, through two access rights with the same domains. The task carries general comments and a completion percentage: its Passed cases over all its cases but the Not applicable ones. Its kanban card counts the cases Not run, Failed and Waiting. As for the checklist, only users with the User access of Project read the percentage and the counts, the task fields testcase_completion, testcase_completion_xml and kanban_testcases, and see them on the card. The Test Cases menu opens filtered on the cases Not run; remove the Not run filter to see all those you can read.

Questions (project.task.question)

The clarifying questions of a task, its Questions (question_ids), are rows in an order of their own:

  • Round: the round of questions the row was asked in, a name or a date.
  • Question and Answer: rich text.
  • Addressed to: the internal user the question is for.
  • Status: Open, Answered or Dropped. A row is Open until it gets an answer that shows something: text, an image, a video or an icon. A create or a write that gives such an answer to an Open row makes it Answered, unless the same call sets the status; a Dropped row stays Dropped. An answer of spaces, empty paragraphs or empty list items leaves the row Open.
  • Answered by and Answered on: who made the row Answered, and when. A create or write that makes a row Answered fills them with the user who makes it, also under sudo(), and the current time; a value the same call gives is kept. A row already Answered keeps them when it is set Answered again or gets another answer. Open clears them and keeps the answer; Dropped leaves them.

A row is named by the text of its question, cut at 80 characters, or of its answer when the question is blank, or else by its task. A row follows the access of its task as a checklist item does, through two access rights with the same domains.

Sessions (project.task.session)

The agent sessions that worked on a task, its Sessions (session_ids), are rows listed the newest first, one per task and session:

  • Session (session_id): the id of the agent session. No link is stored; where the Entire CLI records sessions, entire session info <id> opens it.
  • Date: when the session last wrote its row.
  • Worked by (user_id): an internal user, by default the one who creates the row.
  • Outcome: what the session did, in one line.

A task lists a session once. A create that names a task and a session that already have a row writes the values it gives onto that row and returns it in its place: the date becomes now unless the create gives one, and what it does not give, the user and the outcome included, stays. A batch that names a pair twice keeps the later values. The task and the session are read from the values or their defaults, so a session added to the task’s session_ids, on the task form or with Command.create, updates its row too. A write changes only what it names: editing a row leaves its date alone. A write that moves a row onto a task and session that have a row is refused.

A row is named by its outcome, cut at 80 characters, or else by its session. A row follows the access of its task as a checklist item does, through two access rights with the same domains: it is read with the task, and created, changed and deleted with write access to it, also when a create updates a row. A create, and a write of the task, first checks that the user can read the task it names, so a create on a task the user cannot read is refused whether or not that task lists the session. The Sessions tab, after Pull Requests, shows the rows to project users on the tasks of an AI-driven project, as cards on a phone. Copying a task copies no session.

The lines of a copy

A copy of a task takes the checklist items, test cases and question rows of its source, and its sub-tasks take theirs, unless the values of the copy give its own. What a line keeps depends on the copy:

  • A plain duplicate of a task, a project or a template of either keeps every line as it is: an item with its state and deadline, a case with its result, Verified by, Verified on, Verification and Comments, a row with its answer, status, Answered by and Answered on. A case keeps them under any default Status the copy is made with, of the context or of ir.default, and a Not run case keeps its Verification.
  • A task or a project created from a template, and a project template made from a project, start the lines from zero: items TODO without deadline, cases Not run without verification and comments, rows Open without answer, Answered by and Answered on. An item keeps its description, assignee and reviewer, a case its steps, expected results and Automated test reference, a row its round, question and addressee.
  • The next occurrence of a recurring task, and each of its sub-tasks, starts the items and the cases from zero, as a task created from a template does, and takes no question row. The task it repeats keeps its lines. The occurrence is created as a new task, so its items are posted to their assignee and reviewer.

A task converted to a template is no copy: it keeps its lines.

Pull requests (project.pull.request)

A pull request is a record of its own, shared by every task it belongs to:

  • URL, required and unique, stored in canonical form: scheme and host in lower case, then the path as written, up to and including the number. /files, a query, a fragment or a closing slash after the number are dropped.
  • Repository and Number, read from the URL. The record is named <repository>#<number>, for example owner/repo#12, and is found by that name or by a part of its URL.
  • State: Open, Merged or Closed. A new record is Open.
  • Merge Date, Deploy Date and the Tasks it is linked to.

A pull request link is an http(s) URL with a repository path followed by /pull/N, /merge_requests/N (also /-/merge_requests/N), /pull-requests/N or /pulls/N, N being a number of at most nine digits.

Internal users read pull requests; users with the User access of Project also create and edit them. No access right allows deleting one, and portal users have no access.

Pull requests and Resolution on a task (project.task)

  • Pull Requests (pull_request_ids): the pull requests of the task, on a tab of their own on the tasks of an AI-driven project. Every pull request added to the task or removed from it is tracked in the chatter.
  • Resolution (resolution): how the task was closed: Code, Data, Configuration or No change. It is shown on the tasks of an AI-driven project, and its changes are tracked in the chatter.
  • First Pull Request (pr_uri) reads the link of the task’s first pull request, the one created first, and is empty when the task has none. It is on no view of this module. It is stored, so it can be searched, its changes are tracked in the chatter, and it is writable for the tools that write it over RPC. Writing one pull request link finds the record with that link or creates it, and adds it to the task; a link the task already has changes nothing, and neither does an empty value. Anything that is not exactly one pull request link (other text, a link without http(s)://, a commit or branch link, two links) is refused: a task closed without a pull request takes the Resolution Data, Configuration or No change instead.
  • PR (old value) (pr_legacy), read-only: text that a database upgraded from 16.0 holds there. Nothing on this branch writes it.
  • A copy that keeps the stage of its source takes the Resolution and the pull requests of its source, unless the copy is given its own. That is a plain Duplicate, and every task of a duplicated project. A copy sent to another stage and the copy of a task without a stage take nothing. The next occurrence of a recurring task takes nothing either, in any stage: it is new work. The old value is never copied.
  • A task created from a template, a task template or the tasks of a project created from a project template, takes neither, whatever stage it keeps, and meets the closing rule as a new task: in a marked stage it is refused. A project template with a task sitting in a marked stage cannot be used until that task is moved. A plain Duplicate still takes both.
  • A project template made from a project keeps no Resolution and no pull request of its tasks; the tasks of the project keep theirs. A task converted to a template keeps its own.

The closing rule

On an AI-driven project, Stages Requiring a Resolution (pr_required_states) marks stages. A task of that project enters a marked stage only with a Resolution:

Resolution Pull request Result
empty none refused: choose a Resolution
empty present let through, Resolution = Code
Code none refused: add a pull request
Code present let through
Data, Configuration, No change none let through
Data, Configuration, No change present let through, pull request kept

The rule is checked when the stage of the task changes: on creation, on a write of the stage and on a change of project that moves the task to another stage. The Resolution and the pull request may come in the same write as the stage. Any other stage, a project that is not flagged AI-driven and a write that leaves the stage as it is let everything through, so a task already sitting in a marked stage stays editable. The state of a task (Done, Cancelled) is not part of the rule: a task set Done outside the marked stages needs no Resolution. No context key a caller sends skips the rule.

Templates are outside the rule: a task template, its sub-tasks and the tasks of a project template enter a marked stage without a Resolution.

The next occurrence of a recurring task, created by Odoo when the task it repeats is set Done or Cancelled, enters the first stage of its project, or the stage of that task when the project lists none, unchecked by either rule, its sub-tasks included: a refusal would undo the change of state with it. The task set Done or Cancelled is checked as any task, and so is the occurrence when it is moved into a marked stage later.

The estimate rule

On an AI-driven project, Stages Requiring a Type and an Estimate (estimate_required_states) marks stages. A task of that project enters a marked stage only with a Task Type and an Estimate above zero hours. The refusal names what is missing, the type, the estimate or both, each with the tasks that lack it.

The rule is checked where the closing rule is: on creation, on a write of the stage and on a change of project that moves the task to another stage. The type and the estimate may come in the same write as the stage, and a task created straight into a marked stage needs both in the values of its creation. Any other stage, a project that is not flagged AI-driven and a write that leaves the stage as it is let everything through, so a task already sitting in a marked stage stays editable. No context key a caller sends skips the rule. A stage marked for both rules refuses for the Resolution first. Templates are outside this rule too, and so is the creation of the next occurrence of a recurring task (above).

The next occurrence of a recurring task is a copy of the task, so it carries its task type and its estimate.

The project that develops this Odoo (project.project)

  • Develops This Odoo (develops_this_odoo) marks the AI-driven project whose tasks change the Odoo database the module runs in. One project of the database carries it at most, archived projects included: a second one is refused, and the refusal names the project that has it, also to a user who cannot read that project. Setting it on a project that is not AI-driven, or clearing AI-driven Project on the project that has it, is refused.
  • Only a system administrator (base.group_system) sets or clears it, at creation (a default of the context included) or in a write; a write that leaves it as it is passes for any user. Only a system administrator archives or deletes the project that carries it.
  • The project form shows it to system administrators, below AI-driven Project, on a project that is AI-driven or carries it. A change is tracked in the chatter of the project. A duplicated project starts without it.
  • The task has the same field, related to its project, read-only and readable by every user who reads the task.

Modules of a task (project.task)

  • Modules (module_ids): the installed modules the task touches, records of the module list (ir.module.module). On the tasks of the project that develops this Odoo the form shows them after the Resolution, as tags bearing their technical names, and offers only installed modules. On the tasks of other projects the form hides them; they are kept, and the project does not stop a create or a write of them. A duplicated task starts without modules. A change of the modules is not tracked: Odoo 20 writes tracked values into the text of the chatter message, which every reader of the task reads, whatever the groups of the field.
  • A create or a write refuses a module it adds that is not installed; To be upgraded and To be removed count as installed, To be installed does not. The refusal names the modules, and the whole call is refused, also for a module given as a default of the context. A module already on a task stays there when it is uninstalled: the task saves with it, and a write that keeps it or links it again to that task passes.
  • Module Names (module_names), not stored and on no view: the technical names of the modules, sorted, separated by ", "; False without modules.
  • The task search has a Module field: it finds tasks by a module’s technical name or title.
  • Both fields, and the Module search, are for users with the User access of Project only. They read the module list by an access right of this module.
  • Under the context key module_technical_name a module is named by its technical name instead of its title. The picker passes it, with a list and cards of the technical name and the title, without buttons; the Apps menu keeps the views of base.

The stage log (project.task.stage.log)

One row when a task is created with a stage and one row on every change of its stored stage, for every task of the database, in an AI-driven project or not. The rows are written by SQL where the row of the task is written, in _create and _write_multi of project.task. No context (tracking_disable, mail_notrack, mail_create_nolog) and no sudo() goes around the log, and a stage recomputed by a change of project is logged too, on the task and on the subtasks moved with it.

  • Task, Date and User: the task, when its stage changed and who changed it. Deleting a task deletes its rows.
  • Stage and Stage Name: the stage the task entered. The stage is empty when the task left its stage, and when the stage was deleted since; a deleted stage keeps its name.
  • Previous Stage: the stage the task left. It is empty when there was none and when it was deleted since.
  • Source: Recorded on every row this branch writes. From the chatter, From the last stage update and From the creation date are on the rows of a database upgraded from 16.0.

A task created without a stage gets no row. A task that loses its stage gets a row with an empty stage. A write that carries the stage the task already has writes no row. A task that existed before the module was installed has no row until its stage changes; that first row names the stage it left as the previous one.

Only system administrators (base.group_system) read the log, and no access right allows creating, changing or deleting a row. The log has no view and no menu. A search of the log first flushes the stage changes that are pending.

Task notes (mail.message)

  • Task (task_id): the task a message is posted on, empty for a message of another model and for one whose task no longer exists. It is stored, set from the model and the record of the message, and emptied when the task is deleted.
  • Category (note_category): Requirement Change, Design Decision, Bug Fix, Review Fix, User Feedback, Progress, Revised or Deploy, given to an internal note of a task whose body opens with it in bold. It is stored, and read again when the body, the model, the subtype or the message type of the message changes, as when a note is edited.

Both are computed when a message is created, and for every existing message when the module adds their columns, on install or on the update that brings them.

The category of a note:

  • An internal note is a message of the Note subtype on a task, of any message type but Tracking. A message to the followers, a message on another model and a tracking message get no category, whatever their body.
  • The body opens with the bold text (<b> or <strong>): only white space, &nbsp; and at most one opening tag, <p> or <span>, with or without attributes, come before it.
  • The bold text opens with the category, in any letter case, and ends there or goes on after a dash, a colon, a slash, a plus or an opening parenthesis: <b>Bug Fix</b>: the total, <b>Progress: 2/2</b>, <b>Bug Fix (round 2)</b>. Bold text naming two categories gets the first. <b>Progress report</b> and <b>Deploy notes</b> get none.

Project > Task Notes lists the internal notes of tasks: a message to one user, a tracking message and a message with neither a body nor a file are left out, and so are the notes of tasks the user cannot read, which Odoo would show to their author or recipients. The notes of task templates, of their sub-tasks and of the tasks of project templates are left out too, as core leaves those tasks out of its task lists; the Notes button of such a task counts and lists its own. The domain names the model project.task, so Odoo checks the access of the tasks in SQL. Odoo 20 lets any user group messages under that check: the groups and their counts hold only notes of tasks the user can read. Groups by category come in the order of the categories, the notes without one last.

Images in task texts (project.task.image.mixin)

The images of the texts of a task, a question row or a test case are attachments of that record, on every task of the database, in an AI-driven project or not. The texts are the stored Html fields, neither computed nor translated, of the task (Description, Solution, the general comments of its test cases), of its question rows (Question, Answer) and of its test cases (Steps to execute, Expected results, Comments), those other modules add to these models included, and the html properties of a task’s Properties (task_properties), the defaults its project fills in included, on create and on every write of the task’s project or parent, which also refills the properties of the tasks below it, its other properties left as they are. The editor of the form already uploads an image added in an Html field when the record is saved; the module does the same for every other save.

  • A create or a write that saves a text turns each <img> whose src is a base64 inline image (data:image/...;base64,...), in any letter case and with an entity-encoded scheme too, into an attachment of the record, and its src into /web/image/<id>?access_token=<token>, as the editor and core mail do. The module changes only the src; the field sanitizes the new text as on any save. The image of a question row or a test case is an attachment of the row.
  • The attachment takes the name in the image’s data-filename, data-file-name or alt, the first that is not blank, or else image-<n>.<type>, numbered per record within the save. The same image twice in one save is one attachment.
  • The attachment is created under sudo(), with the user who saves as its creator, once the save has passed its own access checks: a save the user may not make creates none. The new text is stored without a second write: no other chatter message, and no write logic of another module runs again.
  • Core reads the image first (ir.attachment._check_contents), as for every attachment upload, and resizes it as described under Configuration, once. An image it fails to read (an image too large to open) stays inline and the save passes. A lack of memory, the CPU time limit of a worker and a database error fail the save. An SVG moved by a user who may not edit views is stored as text, as core stores such an upload, and no longer displays.
  • The images of a task’s Description, Solution and html properties show among the attachments of the task’s chatter. Deleting a task, a row or a test case deletes its images; a task deletes its rows with theirs.

A task, a question row or a test case created with a text that shows an image of an attachment of another task, row or test case (/web/image/<id>), as a duplicated task and its copied lines, a task created from a template, the next task of a recurrence or a create from another record’s text do, gets its own copy of that attachment, with its own access token, and its text links the copy. A question row or a test case moved to another task copies the images of other records in its texts the same way; its own images stay its own. A copy outlives the record it was made from. Only an image the user saving may see is copied: one they can read, or one whose link carries the attachment’s access token. Under sudo(), the superuser included, only a link with the attachment’s own access token is copied. Any other link stays as it is, and so does a link to another record’s image that a write pastes, or to an image core fails to read or whose file is missing from the filestore.

Texts saved before 20.0.2.13.0 keep their inline images until the text is saved again or _move_inline_images_to_attachments runs on its task (see Usage).

Task brief (project.task)

Brief (brief) is the whole task as Markdown text, for an agent or a tool that reads tasks over RPC. It is computed for the user who reads it, in the language and the companies of their context, and not stored. It is on no view, cannot be exported, and is left out of a read that names no fields; a read that names brief gets it. Its help text is the reference for the forms of urls it rewrites.

A brief holds, in this order, each part only when it has something to show:

  • The header: the task’s key (Task keys below), or #<id> for a task without one, and its title; then the project, the stage and since when, the status (state), the task type, the estimate and its size, the priority, the planned start, the deadline, the hours spent, the assignees, the UAT users, the author and the creation date, the Resolution, the modules on a task of the project that develops this Odoo, the tags, and the link to the task form (/odoo/project.task/<id>). The planned start and the hours spent show where a module declares their fields (planned_date_begin, effective_hours).
  • Related tasks: the parent, the sub-tasks, the tasks it is blocked by and those it blocks, each with its key, title and stage.
  • Pull requests, with their state, merge date and deploy date.
  • The Description.
  • The question rows, each with its id, status, round, addressee, who answered and when, its question and its answer.
  • The Solution.
  • The checklist, its progress counting the Done items over the items not cancelled; each item with its id, state, assignee, reviewer and deadline.
  • The test cases: the general comments, then each case in its order with its id, status, verification (who, when, how), automated test reference, steps, expected results and comments.
  • The sessions, the newest first.
  • The last 10 internal notes with a body, of those the task’s Notes button lists, oldest first, each with its date, author and category. Nothing else is cut.
  • The attachments of the task, each with its name, id, type and size. The images of a question row or a test case are attachments of the row: they show as pointers in its texts, not in this list.

Times are in UTC, the deadline included. The texts become Markdown (headings, emphasis, links, lists, tables, code) with no markup left; the headings of a text sit below the section that holds it. An item of an editor’s checklist is a task list item, - [x] when ticked and - [ ] when not, a nested checklist nested items; the box stands on a line of its own when the item opens with a heading, a list, a table, a rule, a code block or a quote. Another list item that starts like one has its bracket escaped.

  • An image or a link that names an attachment, of the task, of a row or of any other record, by a relative url or a url on the host of this database (get_base_url(), a website’s domain where it applies), in any url form, becomes a pointer: ![image: <name>](attachment <id>) for an image, [file: <name>](attachment <id>) for a bare link and [<link text>](attachment <id>) for a link with a text of its own; ![image](attachment <id>) and [file](attachment <id>) without a name.
  • An inline image the save has not moved to an attachment shows as [image not yet moved to an attachment]: its data never enters the brief.
  • Tokens and credentials are removed from urls: a url loses its user and password, its query and fragment parameters named like a token, and the hash and pid that sign a portal link. That holds for the url of a link or an image, and on a best-effort basis for a url that stands as a word in a text or in code. A token written loose, outside a url, stays.
  • A link of a scheme other than http(s) or mailto keeps only its text.
  • User text that would open a Markdown heading, list, quote, code fence (of three backticks or more), table row or HTML block at the start of a line is escaped, a table delimiter row too, and names are put on one line, so a text cannot open a section of the brief.

A reader who cannot read the task is refused, as a read of it is. What the reader may not read is left out: the lines (question rows, checklist items, test cases, sessions, pull requests), the related tasks, the parent included, the notes and the attachments under their access rights, the companies not selected in their context included; and the fields their groups keep from them, such as the question rows, checklist, test cases, sessions and modules for a user outside Project / User. A many-to-one value of the header (the project, the stage, the author) shows its name as a read of the task does. Archived sub-tasks, blocking and blocked tasks and assignees are left out, also under a context with active_test false; an archived parent or user in a many-to-one value (such as Author, Verified by or Addressed to) still shows.

Task keys (project.project, project.task)

Every project has a Key (key, up to 10 characters), and every task of a project a key of its own (key, up to 20 characters) such as PROJ-12: the key of its project and the next number of the project’s Key Sequence (task_key_sequence_id). Both keys are unique. A task’s display name is its key before the name it has otherwise, so the breadcrumb, lists, cards and references show it, a portal user’s included, and a name search finds projects and tasks by key, as does the search of their lists. A portal user reads a task’s key and finds tasks by it, as everyone does. The task’s url is the link to its form in the web client, /odoo/action-project.action_view_task/<id>.

  • A new project gets the initials of its name in upper case (the first three letters of a one-word name), followed by the lowest counter that makes it free; archived projects count. Only letters and digits make the key: a word of none gives no initial, and a name of none gives no key. A key made of many words is cut to the 10 characters with its counter. The project form proposes the key from the name until one is set.
  • A task gets the next key of its project when it is created; a task created with no project gets none, whatever project the context proposes by default. Moved to another project, it gets a key of the new one, and so do the sub-tasks that move with it, archived ones and those the user cannot read included; moved to a project that gives no key, or taken out of its project, they lose theirs. A sub-task given a parent in another project moves into that project and gets a key of it. A sub-task in a project of its own stays there with its key. Written with its own project, a task keeps its key, and a task without one gets the next key of that project; its sub-tasks, which do not move, are left as they are.
  • A copied task gets the next key of its own project, and none without a project: the copy keeps no key of its source. So does the next occurrence of a recurring task, and a task created from a template.
  • A new project key renames the keys of the project’s tasks and the prefix of its sequence. Each task keeps its number, the digits after the last hyphen of its key, whatever hyphens the former project key held. A task key that does not end in a hyphen and digits, one given by hand or by an import, has no number to keep and stays as it is. A cleared key clears the keys of its tasks, those included; the project gives none until it has a key again, and its sequence then goes on from its next number. The tasks created in it or moved into it meanwhile stay without a key until one is written with its project.
  • A copied project gets a sequence of its own; a deleted project takes its sequence along.
  • /projects/<key> and /tasks/<key> open the form of the project or task of that key, whatever its case, among those the user can read; any other key opens the form of a new task or project. % and _ in a key are no wildcards. The form is the web client’s: a portal user’s /tasks/<key> finds the task but leads to the portal home (/my), where Odoo sends a user outside the web client, not to the task.
  • In a run with test_enable keys are off, unless the context sets test_project_key: the tests of other modules compare display names without keys.

The fields, constraints and sequences carry the names and columns of the 16.0 branch, so a database upgraded from it keeps every key and the next number of every sequence. What the install and the update to 20.0.2.17.0 give a database that lacks keys is under Installation.

Coming from 16.0

The module’s models, fields and selection values carry the names of the 16.0 branch, so a caller written for one branch works on the other, but for is_task_readable (below). What differs on 20.0:

  • The install hook gives the keys a database lacks and nothing else (see Installation). The 16.0 branch’s also takes over the records of the module’s former name, turns old pr_uri text into pull request records, fills the stage log with the past of the tasks, sets the size of every task from its hours, sets hours that are NaN or infinite to zero, converts the test case states, renames the checklist model with its table and external ids, turns the Html questions and answers into question rows and fills the task and the category of existing messages by SQL. Of these, this branch converts only the test case states, by SQL in the migration of 20.0.2.15.0: a task that got such hours under an earlier 20.0 version keeps them, and the constraint on the estimate refuses its copies and its next occurrence until they are corrected. The ORM computes the task and the category of existing messages when the module adds their columns.
  • Task keys do not take the place of OCA project_key: this branch gives the keys whatever else is installed, and a database that ran project_key on Odoo 20 is not provided for. The task’s url and the /projects/<key> and /tasks/<key> redirects lead to /odoo/action-<action>/<id> URLs; an unknown key opens the form of a new record, where 16.0 opens a form of no record. The task form shows the key before the title at all times; on 16.0 outside edit mode only.
  • Checklist items, question rows, session rows and test cases follow the access of their task through the domains of their access rights, with the access operator of Odoo 20: reading follows the read access of the task, a change its write access. On 16.0 items, question rows, session rows and test cases follow the read access of their task for every operation, through two ORM overrides in project.task.access.mixin, which this branch does not have. On 16.0 an item deleted meanwhile passes the access check.
  • This branch has neither is_task_readable nor the grouped read of messages that 16.0 opens to project users on a domain naming it: Odoo 20 groups messages for any user. A client that names is_task_readable fails here.
  • A message that tracks changed fields is of type Tracking on Odoo 20, with the changes in its body after any note logged with them. It has no category and is not in Task Notes.
  • A task opens on Description; Checklist, Technical Solution, Test Cases, Pull Requests and Sessions follow it. On 16.0 Checklist is the first tab.
  • AI-driven Project, Develops This Odoo, Stages Requiring a Resolution and Stages Requiring a Type and an Estimate are settings under Tasks Management on the project form.
  • A plain Duplicate keeps the stage of its source on Odoo 20, so it takes the Resolution and the pull requests as described above. On 16.0 only the tasks of a duplicated project keep their stage.
  • A task has a state next to its stage on Odoo 20. Neither rule reads it.
  • Odoo 20 tracks many2many fields: every pull request added to a task or removed from it is in the chatter. On 16.0 only pr_uri is tracked. A change of the modules leaves no trace on either branch.
  • Odoo 20 creates a task from a template, which takes no Resolution and no pull request and starts its lines from zero, as described above. Odoo 16 has no templates.
  • The rows of the stage log are written in _create and _write_multi, on 16.0 in _create and _write.
  • The estimate is the task’s allocated_hours (Allocated Time), the name planned_hours has in Odoo 20.
  • Odoo 20 itself skips the assignment notification under mail_auto_subscribe_no_notify; on 16.0 the module adds that. Odoo 20 does not refuse a message from an account without an email address: without the key such an account’s writes go through and the notification is queued without a sender address.
  • The image of a question row or a test case is an attachment of the row, as the Odoo 20 editor attaches it, and a link to an image of any task, row or test case is copied. On 16.0 every image is an attachment of the task, and only a link to another task’s image is copied.
  • Odoo 20 stores markup given as an image and a truncated TIFF as they come, so they become attachments; on 16.0 they stay inline.
  • The brief’s header shows the task’s status (state), which Odoo 16 does not have, a deadline with its time, the planned start where a module declares planned_date_begin (on 16.0 the planned window of planned_date_start and planned_date_end), and links the task as /odoo/project.task/<id>.

Installation

Installing the module is all a database needs, but for the two cases below. Its install hook gives the projects and the tasks that exist their keys, as the update to 20.0.2.17.0 does (below). The install adds two columns to the message table and computes them for every message through the ORM: the table stays locked until the module is loaded, which takes long on a large message table.

A database that has an earlier 20.0 version installed

The module has three migrations. 0.0.0/pre-migration.py runs on every version change of the module. Before the data files load, it blanks the stored arch of the module’s extension views, which still name fields and buttons of the earlier version, so that an update from any earlier version passes without dev flags. The data files rewrite each view they name; a view no file names any more is deleted at the end of the update. Translations of those views made in the interface are lost with the blanked arch, on every version change: the module ships none. 20.0.2.15.0/post-migration.py converts the test case states of 20.0.2.4.1 and earlier and 20.0.2.17.0/post-migration.py gives the projects and tasks their keys (below); they are the only migrations that write data. The update:

  • deletes the fields Difficulty, Knowledge Area Level and Tester of the tasks, with their values;
  • deletes the Html fields questions and answers of the tasks, with their columns: their text is not turned into question rows;
  • creates the checklist model project.task.checklist.item with an empty table. The items of the former project.task.subtask stay in the table project_task_subtask, which no model reads. Its foreign key on the assignee restricts deletion: a user assigned to such an item cannot be deleted until the table is dropped by hand;
  • creates the two All checklist updates subtypes under new external ids and deletes the former ones, with the follower subscriptions to them: tick All checklist updates again where it was ticked;
  • gives checklist items, test cases and question rows two access rights each, access_task_<model>_read and access_task_<model>_write (checklist_item, testcase, question), and deletes the access rights no data file names any more, access_task_testcase among them: test cases follow the access of their task from then on;
  • computes the task and the note category of every message, as an install does.

Export the deleted fields first if they are needed.

The update leaves:

  • the external ids that mail (selection values of the activity fields) and phone_validation (the activity mixin inheritance) hold for the former checklist model; nothing reads them;
  • the sizes the tasks have stored, until their hours change.

Of the versions below, only 20.0.2.15.0 and 20.0.2.17.0 have a migration of their own, next to the blanking that runs on every version change.

The update to 20.0.2.9.0 adds the Modules of a task: it creates the table project_task_ir_module_module_rel, the two views of the module picker, the Module field of the task search and an access right that lets project users read the module list. It writes nothing on the tasks, which start without modules. Where base_install_request already lets every internal user read the module list, the access right changes nothing; without it, the field still works for project users.

The update to 20.0.2.10.0 adds Develops This Odoo to projects, with its column, and the same field on tasks, related to the project and not stored. It writes nothing on the projects: no project carries the flag after it, and the form hides the Modules of every task until one does. Afterwards a system administrator sets the flag on the AI-driven project that develops the database.

The updates to 20.0.2.10.1 and 20.0.2.11.1 write nothing on existing records.

The update to 20.0.2.12.0 adds the sessions of a task: the table project_task_session, its two access rights for project users, access_task_session_read and access_task_session_write, and the Sessions tab of the task form. It writes nothing on the tasks, which start without sessions.

The update to 20.0.2.13.0 makes the images of the texts of tasks, question rows and test cases attachments of the record holding the text when a text is saved. It converts no data: a text saved before keeps its inline images until it is saved again, or until a migration or a script calls _move_inline_images_to_attachments on its task (see Usage).

The update to 20.0.2.14.0 adds the Brief of a task, computed on each read that names it. It adds no column, stores nothing and writes nothing on existing records.

The update to 20.0.2.15.0 deletes the test case field Passed (passed) with its column, at its end. A create or write that sends passed, or a former state value (todo, done, cancelled), fails with Odoo’s ValueError. After the data files load, the update converts the test cases stored with a former state, which a database that ran 20.0.2.4.1 or earlier holds, by one SQL statement: todo to not_run, done to passed and cancelled to not_applicable. It logs how many it converts. Until then such a case matched no filter and no kanban count, the completion of its task counted it as not passed, and a copy of its task failed on its state.

The blanking of the extension views takes passed out of the stored test case views of the task form before the data files load. A view of another module that names passed is not blanked: a module that depends on this one rewrites its views from its own files when the update reaches it, and that update fails while a file still names passed; a view without an external id, such as one made in the interface, fails when it is rendered. Change them by hand.

Run the update with the server stopped: dropping the column takes an exclusive lock on the test case table, and workers running the previous code read the column.

The update to 20.0.2.15.1 adds no column and writes nothing on existing records. The html properties of a task saved before it keep their inline images until they are saved again, or until _move_inline_images_to_attachments runs on the task, which covers them from this version on.

The update to 20.0.2.16.0 adds the UAT users of a task (uat_user_ids, table project_task__uat_user_rel) and puts them on the task form after the Assignees; a copy of a task starts without them. It has no migration and writes nothing on the tasks. A database where another module already declares the same field on the same table keeps the table and its rows; when a new version of that module no longer declares the field, update both in the same run.

The update to 20.0.2.17.0 adds the task keys (Task keys in the description): the columns key of projects and tasks with their unique constraints, and task_key_sequence_id of projects. Its migration, as the install hook does, gives the keys the database lacks:

  • Each project without a key, archived ones included, gets one from its name and a sequence. A name without letters or digits gives no key: that project stays without one until somebody types one, which its form requires on the next save. Its tasks created from then on get keys; those it had stay without one, since _set_missing_keys leaves a project that has a key alone, until one is written with its project. Call _number_keyless_tasks on that project from a shell to number them.
  • The tasks without a key of those projects, archived and folded ones included, get the next numbers of the project’s sequence in the order they were created, and the sequence moves past them. One SQL statement writes their keys, so their last update date does not change.
  • A project that has a key, and its tasks, are left alone.
  • A run with test_enable gives no keys, since keys are off in a test run: run the update without it, or call _set_missing_keys on project.project from a shell afterwards.

The update to 20.0.2.18.0 has no migration and writes nothing on existing records. A next occurrence of a recurring task created from then on takes the checklist items and test cases of its task from zero, takes no Resolution and no pull request of its task in any stage, and enters the first stage of its project, or the stage of its task when the project lists none, unchecked by the closing and the estimate rules.

Configuration

  • On a project, switch on AI-driven Project (Settings tab, Tasks Management) to show the Technical Solution, Pull Requests and Sessions tabs and the Resolution on its tasks, and to hide the core priority star on them.
  • Below it, a system administrator (base.group_system) switches on Develops This Odoo on the one AI-driven project whose tasks change this Odoo database: its tasks show their Modules. The setting is shown to system administrators only, on a project that is AI-driven or carries the flag. One project carries it at most, archived projects included: to move it, switch it off on the project that has it, then on on the other one. Only a system administrator archives or deletes the project that carries it.
  • Then, on an AI-driven project, Stages Requiring a Resolution lists the stages a task enters only with a Resolution, and with a pull request when the Resolution is Code. Only stages of the project can be picked. Leave it empty to switch the closing rule off.
  • Below that, Stages Requiring a Type and an Estimate lists the stages a task enters only with a task type and an estimate above zero hours. Only stages of the project can be picked. Leave it empty to switch the estimate rule off.
  • What creates a task straight into a stage of that second list without both values is refused there: the kanban quick create, which takes a title and assignees; an email to the alias of the project, which gives neither value; a sales order line that creates a task, which gives no task type. A copy that keeps the stage of its source, a plain Duplicate or the duplication of a project, takes the type and the estimate of its source, so it is refused only where its source sits in such a stage without them.
  • Checklist items, question rows, session rows and test cases are managed by users with the User access of Project (Settings > Users, the Access Rights tab of a user). Such a user reads the lines of the tasks they can read and creates, changes and deletes those of the tasks they can change: core lets a project user read every task template without project, and so its lines, but change them only where the template may be changed. The Checklist, Test Cases, Technical Solution and Sessions tabs, and the checklist and test case figures of the task’s kanban card, are hidden from users without that access.
  • Project > Task Notes and the Notes button of the task form are shown to users with the User access of Project. They list the notes of the tasks the user can read; the menu leaves out those of templates.
  • Pull requests are read by every internal user and created and edited by users with the User access of Project. No access right allows deleting one.
  • The Modules of a task, on the form and in the task search, are shown to users with the User access of Project only.
  • The stage log is read by system administrators (base.group_system) only. No access right allows creating, changing or deleting a row.
  • To be notified of checklist items of which you are neither the assignee nor the reviewer, edit your follower subscription on the task or on the project and tick All checklist updates.
  • An integration that writes tasks or checklist items passes mail_auto_subscribe_no_notify in the context to keep the write silent: no assignment notification, no checklist post. Without the key the notifications are queued as for any user, also for an account that has no email address to send them from.
  • The images that task texts give to attachments follow core’s system parameters for every attachment upload: an image larger than base.image_autoresize_max_px (1920x1920 by default, 0 to keep every size), of a type listed in base.image_autoresize_extensions (png,jpeg,bmp,tiff), is resized at the quality of base.image_autoresize_quality (80).

Usage

On the task form, which opens on Description:

  • Set Priority, Estimate (in hours) and Task Type next to the tags. Size shows the size of the estimate and cannot be edited.
  • Add the UAT users, the people who run the acceptance tests of the task, after the Assignees.
  • Checklist tab: add items, each with an Assigned to user, yourself unless you pick another, and an optional deadline. You are the reviewer of the items you add. A new task or sub-task saves with the items added before its first save: they are created right after the task, as items added to it once saved. The assignee or the reviewer moves an item with the state icons (TODO, Waiting, Done, Cancelled), changes its description or gives it another assignee. They also convert it into a sub-task of the task with the Convert to Sub-task icon of its row, after a confirmation: the item is deleted and a note on the task links the sub-task. The icon shows only to who may convert: on a task you may change, the assignee, or the reviewer when they may open the task’s project. On a task template without a project the reviewer converts only as a project manager; a private task shows no icon. The task’s kanban card shows your own completion percentage, only when you have non-cancelled items assigned to you.
  • Technical Solution tab (AI-driven projects): the Questions list, then the Solution. Add a row per question, with its round and the user it is addressed to, and drag the rows into order. Give a row its answer and it becomes Answered, stamped with your name and the time; the status of a new row follows its answer. Once the row is saved, set it back to Open to ask again, or to Dropped when it no longer applies. The Answer column is hidden in the list until you show it. On a phone the list shows cards.
  • Test Cases tab: add ordered cases with steps and expected results, then give each case its result with the icons of its row; a row offers the states other than its own (Passed, Failed, Not run, Waiting, Not applicable). Verified by and Verified on show who gave the last Passed or Failed. On a phone the tab shows cards with the same buttons. Set Verification to Automated test or Demo, and the Automated test reference, on the form of the case.
  • Notes button: counts the notes of the task and opens them in the Task Notes list. It shows once the task has a note. On a template it lists the notes the Task Notes menu leaves out.
  • Pull Requests tab (AI-driven projects): add the pull requests of the task. The list shows the link, state, merge date and deploy date of each. A pull request already recorded for another task is picked from the list instead of being created again. PR (old value) shows above the list on a task that has one.
  • Sessions tab (AI-driven projects, project users), after Pull Requests: the agent sessions that worked on the task, the newest first, with their date, who worked them, the session id and the outcome; cards on a phone. A row saved with a session the task already lists updates that row instead of adding one. Editing a row leaves its date as it is.
  • Resolution (AI-driven projects), next to the tags: choose it before moving the task to a stage that requires one. Code needs a pull request on the task; a task that already has one gets Code by itself.
  • Modules (the project that develops this Odoo, project users), after the Resolution: the installed modules the task touches, as tags bearing their technical names. Type a technical name or a title to pick one; only installed modules are offered, and Search More… lists them by technical name and title, cards on a phone. A module that is not installed is refused, and the refusal names it. A module uninstalled after it was added stays on the task, which still saves with it. Search tasks by Module, with a technical name or a title.
  • Task Type and Estimate (AI-driven projects): set both before moving the task to a stage that requires them. The refusal names what is missing.

An image pasted or dropped into a text of a task, of a question row or of a test case, or into an html property of a task, becomes an attachment of that record when it is saved, and the text shows it from there; the images of the Description, the Solution and the html properties show among the attachments of the task’s chatter. A duplicated task and its lines get their own copies of the images.

Project > Checklist lists the checklist items of the tasks you can read in the selected companies, opened on your own TODO items. Group by project, task, user or status. The assignee or the reviewer converts an item into a sub-task with Convert to Sub-task in the header of its form, where they may convert it from the task: the new sub-task opens in place of the item, without breadcrumbs back to it.

Project > Test Cases lists the test cases of the tasks you can read, opened on the ones Not run: a list, cards on a phone. Filter on Not run or Failed, group by project, task, status or verification. The header of a case’s form gives it its result with the same buttons, next to its status bar: Not run, Passed and Failed, and the status of the case when it is another.

Project > Pull Requests lists all pull requests, the newest first: a list, cards on a phone. Search by URL, repository or task, filter on Open, Merged, Closed or No State, group by repository or state. On the form of a pull request, set State, Merge Date and Deploy Date when it is merged and deployed.

Project > Task Notes lists the internal notes of the tasks you can read, archived tasks included, templates and the tasks of project templates left out, the newest first: a list, cards on a phone. A note of files alone is listed; a message to one user and a change of tracked fields are not. Filter on a category, search by contents, task or author, and group by category or by task: a task’s group bears its current name. A note opens read-only with its files, and Open Task opens its task. Nothing is created, changed or deleted from this menu.

To give a note a category, log it on the task with the category in bold as its first words, alone in the bold or followed there by a dash, a colon, a slash, a plus or an opening parenthesis: Design Decision - keep the flow; Progress: 2/3.

A tool that writes over RPC sets pr_uri on the task to the link of the pull request, one link per write, or resolution to data, configuration or no_change when there is none. A write of another link adds a second pull request to the task. The estimate is written to allocated_hours and the type to task_type; a tshirt_estimate sent with them is ignored. The estimate is a finite number: a NaN or an infinity is refused, in any project.

A tool that records the modules of a task over RPC, as a project user, first reads develops_this_odoo on the task and goes on only when it is True: on a task of any other project the form hides the modules, but its project does not stop a write of them. It finds their ids with search_read on ir.module.module, the domain [("name", "in", <technical names>), ("state", "in", ["installed", "to upgrade", "to remove"])] and the field name, then writes module_ids on the task with one (4, <module id>) command per module: the modules already on the task stay as they are. A write that adds a module that is not installed is refused as a whole. It reads the technical names from module_names: sorted, separated by ", ", False when the task has no module.

A tool that keeps a checklist over RPC creates project.task.checklist.item records with task_id, name and user_id, which defaults to the tool’s own user, and reads the items of a task from checklist_item_ids. Items sent with Command.create in the checklist_item_ids of a task being created are created right after the task, with the access rights of the calling user: a portal collaborator gets an access error. It moves an item by writing state (todo, waiting, done or cancelled) as the item’s assignee or reviewer, and turns items into sub-tasks with action_convert_to_subtask, one sub-task under the task of each item, as the item’s assignee, or as its reviewer where its user may read the task’s project or, on a task template without a project, is a project manager (never on a private task); can_convert tells whether its user may, in the companies of allowed_company_ids when the context has it. It reads only the items of the tasks its user can read, and creates, changes and deletes only those of the tasks its user can change; without allowed_company_ids in the context, those of all the user’s companies. It reaches question rows and test cases the same way.

A tool that keeps the questions of a task over RPC creates project.task.question records with task_id and question, and round, addressed_to_id and answer when it has them, and reads the rows of a task from question_ids. It answers a row by writing answer; state takes open, answered or dropped. A create or write that makes a row Answered fills answered_by_id and answered_on unless it sends them.

A tool that records an agent session on a task over RPC, when the session closes, creates a project.task.session record with task_id, session_id and outcome: one create per task, without a search first. The first call for a task and session creates the row, with user_id the tool’s user and date now unless it sends them. A later call for the same pair updates that row and returns its id: date becomes now unless the call sends one, and user_id and outcome stay unless it sends them. A batch create returns one id per values, in their order, the same id where a pair repeats. Command.create in the session_ids of a task updates the same way. It reads the rows of the tasks its user can read, and creates and updates only those of the tasks its user can change: a create on another task raises an access error. It reads the sessions of a task from session_ids.

A tool that gives test case results over RPC writes state on project.task.testcase, and reads the result from it: not_run, passed, failed, waiting or not_applicable. A create or write of passed or failed fills verified_by_id and verified_on unless it sends them. It sends verification_kind (manual, automated or demo) and test_reference with the result: only the buttons set manual by themselves. A create or write that sends not_run clears verified_by_id, verified_on and verification_kind, also the values it sends for them, and leaves test_reference. To prepare a case with its kind before its run, create it without state, or write verification_kind alone on a case Not run: the case keeps it.

A tool reads the notes of one category of a task with search_read on mail.message, the domain [("task_id", "=", <task id>), ("note_category", "=", "design_decision")] and fields such as date, author_id and body. note_category takes requirement_change, design_decision, bug_fix, review_fix, user_feedback, progress, revised or deploy. It reaches the messages its user can read, and groups them under the same check. It gives a note a category by posting it on the task with message_post, subtype_xmlid mail.mt_note and a body that opens with the category in bold, in a paragraph: <p><b>Progress</b> - in review</p>. A body of more than one node that opens with an inline tag and holds no block tag, such as <b>Progress</b> - in review, is stored inside a <span> and gets its category too.

The stage log has no view and no menu. A system administrator reads project.task.stage.log over RPC: the rows come ordered by date, each with task_id, previous_stage_id, stage_id, stage_name, date, user_id and source (live on every row this branch writes). The log holds the stages of every task, also of tasks a user cannot read: code that shows it to other users reads it with sudo(), for the tasks those users can read.

A tool that writes a text over RPC may send its images inline, as <img src="data:image/png;base64,..." data-filename="...">: the create or write makes each an attachment of the record holding the text, and a read of the text gives the /web/image/<id>?access_token=<token> link in its place. To show an image of another task, question row or test case in a new record, it sends the link as it read it, access token included: the new record gets its own copy.

A migration or an odoo shell script moves the inline images of texts saved before 20.0.2.13.0 with _move_inline_images_to_attachments(dry_run=False, store=True) on the tasks, a private method that RPC cannot call. It covers the texts of the tasks and of their question rows and test cases, and the html properties of the tasks, and returns records (how many tasks and rows have texts that change), images (how many attachments it creates), bytes (their size before core resizes them) and texts ({record: {field name: new text}}, the new task_properties a {property name: value} dict of all its values, to store as JSON). An image core fails to read stays inline and counts nowhere. It holds every new text until it returns: run it over the tasks in batches.

  • dry_run=True creates and changes nothing, counts as a run would, and returns empty texts.
  • store=False creates the attachments and leaves the texts to the caller, which can store them by SQL to keep write_date and write_uid; the default stores them as a save does, which updates both. A returned text the caller does not store keeps its inline images, and the next run attaches them again.

An agent or a tool reads a whole task with one read that names the brief: read([<task id>], ["brief"]) on project.task, or search_read with ["brief"] as its fields. A read that names no fields, read() or a search_read without fields, leaves the brief out, so that it does not compute one brief per task it returns; a read of several tasks that names brief computes one brief each. The brief holds what the tool’s user may read, and a task they cannot read raises an access error. Code on the server reads task.brief at the cost of that task’s brief alone, from a recordset of any size.

The rows of the brief carry the ids a tool acts on: ### Question <id> (<status>) for a question row, - <id> <state>: <description> for a checklist item, ### Test case <id>: <name> (<status>) for a test case, and (attachment <id>, ...) in the attachments list. A pointer in a text names an ir.attachment, of the task or of the row whose text shows it:

  • ![image: <name>](attachment <id>), or ![image](attachment <id>), an image;
  • [file: <name>](attachment <id>), or [file](attachment <id>), a bare link to a file;
  • [<link text>](attachment <id>), a link with a text of its own.

The tool reads the file it needs from ir.attachment by that id, under its own rights. [image not yet moved to an attachment] stands for an inline image of a text saved before 20.0.2.13.0. Notes older than the last 10 are read with search_read on mail.message, as above. The help text of the field is the reference for the tokens and credentials removed from urls, and for the forms that may keep them.

Known issues / Roadmap

  • The path of a pull request link is stored as written. Two spellings of one pull request (Owner/Repo and owner/repo, http and https, with and without /-/) are two records.
  • Nothing reads a pull request from its host: State, Merge Date and Deploy Date are set by hand or over RPC.
  • A module that a pull request of the task brings into the code base is added to the task only once it is installed in the database.
  • Deleting a module from the module list, which Odoo refuses for a module installed or about to be, takes it off every task that held it.
  • The closing rule and the estimate rule are checked on the tasks of a write that names their stage or their project. A stage recomputed for another reason is not checked, as for a subtask whose parent changes project.
  • A module that writes a task’s new project on its own, before the other values of the same write, runs both rules before the Resolution, the task type and the estimate of that write arrive. Setting them in an earlier write avoids it.
  • Neither rule is run when a stage gets marked or a project gets flagged, nor on the next occurrence of a recurring task, so a task can sit in a marked stage without what the stage requires: a Resolution, a pull request, a task type or an estimate. Such a task cannot be duplicated, and it stops the duplication of its project, until it gets it.
  • The next occurrence of a recurring task is exempt from both rules by a key in the context of its creation: a task that an automation of an administrator, run on creation, creates inside that creation is exempt too.
  • A checklist item is not converted into a sub-task while the first unfolded stage of its AI-driven project is marked for either rule: the sub-task enters that stage without a Resolution, a task type or an estimate. The item stays. An item of a template converts.
  • The priority star is hidden on the views the description lists. The portal keeps it: the project sharing views, the task list and the task page.
  • The task list of a flagged project drops its Priority column only when opened from the project, which tells it the project is flagged. Reloaded from its address, reached back from an embedded action or opened from a milestone, it shows the column with the stars hidden, as core shows its Milestone column there. A task opened from that list passes the flag on, whatever its own project: the Sub-tasks, Dependent Tasks, Tasks in Recurrence and parent task it opens have no Priority column, tasks of other projects included. The same task opened from another list passes nothing.
  • Leaving template status is not a change of stage: a task template undone, a project template turned back into a project or a template task moved to another project keeps its stage unchecked by either rule.
  • A sub-task that sits in a marked stage without what the stage requires stops a project template being made from its project, as it stops the duplication of the project: core creates its copy in that project first.
  • The sizes stored by an earlier 20.0 version of the module stay as they are until the hours of their task change: this branch has no migration that recomputes them.
  • An update from an earlier 20.0 version converts no data but the test case states: the former checklist items stay in a table nothing reads, and the Html questions and answers are deleted (see Installation).
  • Question rows have no chatter: a change of status or answer leaves no trace but Answered by and Answered on.
  • Session rows have no chatter either: a session that writes its row again replaces its date, and its outcome when it sends one; the former values are not kept.
  • Two first creates of the same task and session in concurrent transactions both find no row: the later one fails on the unique constraint, and nothing retries it.
  • A note whose category is in bold inside a heading or a list, or coloured, gets no category: only one opening <p> or <span> may come before the bold, and nothing between the bold and the category.
  • The eight categories and their spelling are fixed in the module: Bugfix or Deployment in bold is no category. A change of them gives existing notes a category only where a migration recomputes it.
  • A note that code logs with a change of tracked fields (_track_set_log_message) is part of the tracking message of the change: it gets no category and is not in Task Notes.
  • The stage log starts when the module is installed: the stages a task went through before that are not in it.
  • A row of the stage log is written when the change of stage is flushed to the database. Several changes of a task’s stage within one flush are one row, from the stored stage to the last one, and a change undone within one flush leaves none.
  • A stage written by raw SQL is not logged.
  • The user of a row is the one the update leaves on the task as its last writer. When the last writer does not change, that is the user of the environment that flushes the change: the acting user in an ordinary request, also under sudo().
  • The stage name of a row is the source-language name (en_US) of the stage when the row was written.
  • An image is attached once per save: the same image pasted again in a later save becomes another attachment of the record.
  • Only the src of an <img> is read. An image in a srcset, a <picture> source or a CSS background stays as it is, inline or linked, and so does an absolute link to another record’s image (https://<host>/web/image/<id>): a copy of the text still links the source record’s attachment.
  • A file of another record linked as /web/content/<id> keeps pointing at that record’s attachment in a copied text, and the link breaks when that record is deleted.
  • An image taken out of a text stays an attachment of its record.
  • The brief removes tokens from a url that stands as a word of a text or of code on a best-effort basis: a url split by markup (bold, a line break), or holding a brace, < or >, or a bracket or a quote in its query, may keep its token. A token written loose, outside a url, stays as written.
  • The brief is computed on each read that names it, for each task of the read: a read of many tasks naming brief costs one brief per task.
  • The brief holds the last 10 internal notes of the task; older ones are read from mail.message.

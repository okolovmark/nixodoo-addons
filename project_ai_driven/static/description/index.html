Project AI-driven

Additions to project tasks for AI-driven development: task attributes, clarifying questions as rows with their answers, the technical solution, a checklist and test cases per task, pull requests as records, the internal notes of tasks by category, and two rules on the stages a project marks: a Resolution to enter some, a task type and an estimate to enter others. The module also logs the stage changes of every task of the database.

Task attributes (project.task)

  • Priority (Highest to Lowest), Estimate, Size and Task Type (Feature, Bug, Improvement, Investigation, Milestone, Support, Technical Debt), next to the tags on the task form. The type is also a column of the task list; its tracking messages name the field AI-driven Task Type. Neither the type nor the estimate has a default value.
  • Estimate is the core field allocated_hours (Allocated Time), in hours. Size (tshirt_estimate) is stored, read-only and follows it: XS up to 2 hours, S up to 6, M up to 12, L up to 32, XL up to 60, XXL above; empty while the estimate is not above zero. A size sent in a write is dropped and one sent at creation is recomputed from the hours; neither call is refused. With Task Logs (hr_timesheet) installed, timesheet users also see the same field as Allocated Time on the tasks of a project that uses timesheets.
  • The core priority star is hidden on the tasks of a project flagged AI-driven Project: on the form, its Sub-tasks and Blocked By lists, the kanban card, the task list and the calendar popover. Its stored value is not touched: core still orders tasks by it, and the Priority filters of the search still search on it. The tasks of other projects keep the star, also in the same list. The task list of a flagged project opened from the project has no Priority column at all.
  • A Technical Solution tab with the Questions list and the Solution, shown to project users on the tasks of a project flagged AI-driven Project.

Checklist (project.task.checklist.item)

Task-level checklist items, the Checklist of the task (checklist_item_ids), each with a description, an Assigned to user, a Reviewer, a deadline and a state: TODO, Waiting, Done, Cancelled. A new item’s assignee and reviewer default to the user who creates it, on the form and over RPC; the reviewer is read-only on the form. Items have no activities.

An item is found, read, changed, deleted and created by the users who can read its task, archived or not: its access right carries the domain [('task_id', 'access', 'read')], so the record rules of the task apply to its items, the companies selected in the company switcher included. The superuser and sudo() reach every item. Reading, changing or deleting an item deleted meanwhile raises MissingError, as core does.

Only the assignee or the reviewer of an item changes its state, description or assignee. The check runs before the write, against the assignee and the reviewer the item has then: the assignee may hand the item over and change its state in one write, another user cannot take it. The deadline, and the reviewer over RPC, are changed by anyone who can change the item.

A creation and a change of state, description or assignee make one post per item on the task, addressed to the item’s assignee and reviewer, and to its former assignee on a change of assignee, other than the user making the change, under the internal All checklist updates subtype. When no one else is left, the post is a note addressed to no one. A change of description shows the former description under the former state. A post is written in the language of the user making the change. The subtype is not subscribed by default: other followers receive the posts of others only after opting into All checklist updates on the task or on its project. The mail_auto_subscribe_no_notify context key silences these posts, the way it silences the assignment notification of a task in Odoo itself: an integration writes tasks and checklist items with it and nobody is notified.

The task’s kanban card shows the current user’s completion percentage over their non-cancelled items and the number of their TODO and Waiting items. The Checklist menu opens on your own TODO items (the My and TODO filters are on by default); remove those filters to see every item you can read.

Test cases (project.task.testcase)

Ordered test cases per task with Steps to execute, Expected results and Comments. The Status of a case is its result: Not run (the default), Passed, Failed, Waiting or Not applicable.

  • Verified by and Verified on: who gave the last Passed or Failed, and when. A create or write that sets Passed or Failed fills them with the user who makes it, also under sudo(), and the current time; a value the same call gives is kept. Passed or Failed given again is a new verification. Not run clears them and Verification; Waiting and Not applicable leave them.
  • Verification: Manual, Automated test or Demo. A result button other than Not run sets it to Manual when it is empty.
  • Automated test reference: the automated test that verifies the case, such as a test selector. Not run leaves it.
  • Passed (passed) is stored, read-only and follows the status: set for Passed only.

The task carries general comments and a completion percentage: its Passed cases over all its cases but the Not applicable ones. Its kanban card counts the cases Not run, Failed and Waiting. The Test Cases menu opens filtered on the cases Not run; remove the Not run filter to see them all. Copying a task also copies its checklist items, keeping their states, and its test cases, keeping their status, Verified by, Verified on, Verification and Automated test reference: a duplicate and its sub-tasks, a duplicated project, a task or project created from a template, a project made into a template. The next occurrence of a recurring task gets neither.

Questions (project.task.question)

The clarifying questions of a task, its Questions (question_ids), are rows in an order of their own:

  • Round: the round of questions the row was asked in, a name or a date.
  • Question and Answer: rich text.
  • Addressed to: the internal user the question is for.
  • Status: Open, Answered or Dropped. A row is Open until it gets an answer that shows something: text, an image, a video or an icon. A create or a write that gives such an answer to an Open row makes it Answered, unless the same call sets the status; a Dropped row stays Dropped. An answer of spaces, empty paragraphs or empty list items leaves the row Open.
  • Answered by and Answered on: who made the row Answered, and when. A create or write that makes a row Answered fills them with the user who makes it, also under sudo(), and the current time; a value the same call gives is kept. A row already Answered keeps them when it is set Answered again or gets another answer. Open clears them and keeps the answer; Dropped leaves them.

A row is named by the text of its question, cut at 80 characters, or of its answer when the question is blank, or else by its task. A row is found, read, changed, deleted and created by the users who can read its task, as a checklist item is. Copying a task copies its rows with all their values, the status, Answered by and Answered on included, sub-tasks too; the next occurrence of a recurring task gets none.

Pull requests (project.pull.request)

A pull request is a record of its own, shared by every task it belongs to:

  • URL, required and unique, stored in canonical form: scheme and host in lower case, then the path as written, up to and including the number. /files, a query, a fragment or a closing slash after the number are dropped.
  • Repository and Number, read from the URL. The record is named <repository>#<number>, for example owner/repo#12, and is found by that name or by a part of its URL.
  • State: Open, Merged or Closed. A new record is Open.
  • Merge Date, Deploy Date and the Tasks it is linked to.

A pull request link is an http(s) URL with a repository path followed by /pull/N, /merge_requests/N (also /-/merge_requests/N), /pull-requests/N or /pulls/N, N being a number of at most nine digits.

Internal users read pull requests; users with the User access of Project also create and edit them. No access right allows deleting one, and portal users have no access.

Pull requests and Resolution on a task (project.task)

  • Pull Requests (pull_request_ids): the pull requests of the task, on a tab of their own on the tasks of an AI-driven project. Every pull request added to the task or removed from it is tracked in the chatter.
  • Resolution (resolution): how the task was closed: Code, Data, Configuration or No change. It is shown on the tasks of an AI-driven project, and its changes are tracked in the chatter.
  • First Pull Request (pr_uri) reads the link of the task’s first pull request, the one created first, and is empty when the task has none. It is on no view of this module. It is stored, so it can be searched, its changes are tracked in the chatter, and it is writable for the tools that write it over RPC. Writing one pull request link finds the record with that link or creates it, and adds it to the task; a link the task already has changes nothing, and neither does an empty value. Anything that is not exactly one pull request link (other text, a link without http(s)://, a commit or branch link, two links) is refused: a task closed without a pull request takes the Resolution Data, Configuration or No change instead.
  • PR (old value) (pr_legacy), read-only: text that a database upgraded from 16.0 holds there. Nothing on this branch writes it.
  • A copy that keeps the stage of its source takes the Resolution and the pull requests of its source, unless the copy is given its own. That is a plain Duplicate, and every task of a duplicated project. A copy sent to another stage and the copy of a task without a stage take nothing. The next occurrence of a recurring task takes nothing either, unless it starts in the stage of the task it repeats. The old value is never copied.
  • A task created from a template, a task template or the tasks of a project created from a project template, takes neither, whatever stage it keeps, and meets the closing rule as a new task: in a marked stage it is refused. A project template with a task sitting in a marked stage cannot be used until that task is moved. A plain Duplicate still takes both.
  • A project template made from a project keeps no Resolution and no pull request of its tasks; the tasks of the project keep theirs. A task converted to a template keeps its own.

The closing rule

On an AI-driven project, Stages Requiring a Resolution (pr_required_states) marks stages. A task of that project enters a marked stage only with a Resolution:

Resolution Pull request Result
empty none refused: choose a Resolution
empty present let through, Resolution = Code
Code none refused: add a pull request
Code present let through
Data, Configuration, No change none let through
Data, Configuration, No change present let through, pull request kept

The rule is checked when the stage of the task changes: on creation, on a write of the stage and on a change of project that moves the task to another stage. The Resolution and the pull request may come in the same write as the stage. Any other stage, a project that is not flagged AI-driven and a write that leaves the stage as it is let everything through, so a task already sitting in a marked stage stays editable. The state of a task (Done, Cancelled) is not part of the rule: a task set Done outside the marked stages needs no Resolution. No context key skips the rule.

Templates are outside the rule: a task template, its sub-tasks and the tasks of a project template enter a marked stage without a Resolution.

The estimate rule

On an AI-driven project, Stages Requiring a Type and an Estimate (estimate_required_states) marks stages. A task of that project enters a marked stage only with a Task Type and an Estimate above zero hours. The refusal names what is missing, the type, the estimate or both, each with the tasks that lack it.

The rule is checked where the closing rule is: on creation, on a write of the stage and on a change of project that moves the task to another stage. The type and the estimate may come in the same write as the stage, and a task created straight into a marked stage needs both in the values of its creation. Any other stage, a project that is not flagged AI-driven and a write that leaves the stage as it is let everything through, so a task already sitting in a marked stage stays editable. No context key skips the rule. A stage marked for both rules refuses for the Resolution first. Templates are outside this rule too.

The next occurrence of a recurring task is a copy of the task, so it carries its task type and its estimate.

The stage log (project.task.stage.log)

One row when a task is created with a stage and one row on every change of its stored stage, for every task of the database, in an AI-driven project or not. The rows are written by SQL where the row of the task is written, in _create and _write_multi of project.task. No context (tracking_disable, mail_notrack, mail_create_nolog) and no sudo() goes around the log, and a stage recomputed by a change of project is logged too, on the task and on the subtasks moved with it.

  • Task, Date and User: the task, when its stage changed and who changed it. Deleting a task deletes its rows.
  • Stage and Stage Name: the stage the task entered. The stage is empty when the task left its stage, and when the stage was deleted since; a deleted stage keeps its name.
  • Previous Stage: the stage the task left. It is empty when there was none and when it was deleted since.
  • Source: Recorded on every row this branch writes. From the chatter, From the last stage update and From the creation date are on the rows of a database upgraded from 16.0.

A task created without a stage gets no row. A task that loses its stage gets a row with an empty stage. A write that carries the stage the task already has writes no row. A task that existed before the module was installed has no row until its stage changes; that first row names the stage it left as the previous one.

Only system administrators (base.group_system) read the log, and no access right allows creating, changing or deleting a row. The log has no view and no menu. A search of the log first flushes the stage changes that are pending.

Task notes (mail.message)

  • Task (task_id): the task a message is posted on, empty for a message of another model and for one whose task no longer exists. It is stored, set from the model and the record of the message, and emptied when the task is deleted.
  • Category (note_category): Requirement Change, Design Decision, Bug Fix, Review Fix, User Feedback, Progress, Revised or Deploy, given to an internal note of a task whose body opens with it in bold. It is stored, and read again when the body, the model, the subtype or the message type of the message changes, as when a note is edited.

Both are computed when a message is created, and for every existing message when the module adds their columns, on install or on the update that brings them.

The category of a note:

  • An internal note is a message of the Note subtype on a task, of any message type but Tracking. A message to the followers, a message on another model and a tracking message get no category, whatever their body.
  • The body opens with the bold text (<b> or <strong>): only white space, &nbsp; and at most one opening tag, <p> or <span>, with or without attributes, come before it.
  • The bold text opens with the category, in any letter case, and ends there or goes on after a dash, a colon, a slash, a plus or an opening parenthesis: <b>Bug Fix</b>: the total, <b>Progress: 2/2</b>, <b>Bug Fix (round 2)</b>. Bold text naming two categories gets the first. <b>Progress report</b> and <b>Deploy notes</b> get none.

Project > Task Notes lists the internal notes of tasks: a message to one user, a tracking message and a message with neither a body nor a file are left out, and so are the notes of tasks the user cannot read, which Odoo would show to their author or recipients. Its domain names the model project.task, so Odoo checks the access of the tasks in SQL. Odoo 20 lets any user group messages under that check: the groups and their counts hold only notes of tasks the user can read. Groups by category come in the order of the categories, the notes without one last.

Coming from 16.0

The module’s models, fields and selection values carry the names of the 16.0 branch, so a caller written for one branch works on the other, but for is_task_readable (below). What differs on 20.0:

  • The module has no install hook, and its one migration converts no data (see Installation). The 16.0 branch takes over the records of the module’s former name, turns old pr_uri text into pull request records, fills the stage log with the past of the tasks, sets the size of every task from its hours, sets hours that are NaN or infinite to zero, converts the test case states, renames the checklist model with its table and external ids, turns the Html questions and answers into question rows and fills the task and the category of existing messages by SQL. This branch does none of it: a task that got such hours under an earlier 20.0 version keeps them, and the constraint on the estimate refuses its copies and its next occurrence until they are corrected. The ORM computes the task and the category of existing messages when the module adds their columns.
  • A checklist item and a question row follow the access of their task through the domain of their access right, with the access operator of Odoo 20. 16.0 has two ORM overrides for it, in project.task.access.mixin, which this branch does not have. On 16.0 an item deleted meanwhile passes the access check.
  • This branch has neither is_task_readable nor the grouped read of messages that 16.0 opens to project users on a domain naming it: Odoo 20 groups messages for any user. A client that names is_task_readable fails here.
  • A message that tracks changed fields is of type Tracking on Odoo 20, with the changes in its body after any note logged with them. It has no category and is not in Task Notes.
  • A task opens on Description; Checklist, Technical Solution, Test Cases and Pull Requests follow it. On 16.0 Checklist is the first tab.
  • AI-driven Project, Stages Requiring a Resolution and Stages Requiring a Type and an Estimate are settings under Tasks Management on the project form.
  • A plain Duplicate keeps the stage of its source on Odoo 20, so it takes the Resolution and the pull requests as described above. On 16.0 only the tasks of a duplicated project keep their stage.
  • A task has a state next to its stage on Odoo 20. Neither rule reads it.
  • Odoo 20 tracks many2many fields: every pull request added to a task or removed from it is in the chatter. On 16.0 only pr_uri is tracked.
  • Odoo 20 creates a task from a template, which takes no Resolution and no pull request, as described above. Odoo 16 has no templates.
  • The rows of the stage log are written in _create and _write_multi, on 16.0 in _create and _write.
  • The estimate is the task’s allocated_hours (Allocated Time), the name planned_hours has in Odoo 20.
  • Odoo 20 itself skips the assignment notification under mail_auto_subscribe_no_notify; on 16.0 the module adds that. Odoo 20 does not refuse a message from an account without an email address: without the key such an account’s writes go through and the notification is queued without a sender address.

Installation

The module has no install hook. Installing it is all a database needs, but for the two cases below. The install adds two columns to the message table and computes them for every message through the ORM: the table stays locked until the module is loaded, which takes long on a large message table.

A database that has an earlier 20.0 version installed

The update runs one migration, 20.0.2.8.1/pre-migration.py. Before the data files load, it blanks the stored arch of the module’s extension views, which still name fields and buttons of the earlier version, so that the update passes without dev flags. The data files rewrite each view they name; a view no file names any more is deleted at the end of the update. The migration converts no data. The update:

  • deletes the fields Difficulty, Knowledge Area Level and Tester of the tasks, with their values;
  • deletes the Html fields questions and answers of the tasks, with their columns: their text is not turned into question rows;
  • creates the checklist model project.task.checklist.item with an empty table. The items of the former project.task.subtask stay in the table project_task_subtask, which no model reads. Its foreign key on the assignee restricts deletion: a user assigned to such an item cannot be deleted until the table is dropped by hand;
  • creates the two All checklist updates subtypes under new external ids and deletes the former ones, with the follower subscriptions to them: tick All checklist updates again where it was ticked;
  • computes the task and the note category of every message, as an install does.

Export the deleted fields first if they are needed.

The update leaves:

  • the test cases with the states of the earlier version (todo, done, cancelled) as they are stored, with their Passed flag. Such a case matches no filter and no kanban count of this version, and the completion of its task counts it as not passed, until it is given a result;
  • the external ids that mail (selection values of the activity fields) and phone_validation (the activity mixin inheritance) hold for the former checklist model; nothing reads them;
  • the sizes the tasks have stored, until their hours change.

A database that has the 20.0 project_software installed

project_software is the former name of this module. Such a database is not updated in place. With the code of project_ai_driven on the addons path:

  1. Install project_ai_driven.
  2. Uninstall project_software.

What to expect:

  • The tasks keep their field values and their test cases, the test case states as they are stored.
  • The checklist items and the Html questions and answers are not kept: project_ai_driven declares neither project.task.subtask nor the two fields. The uninstall drops the two fields with their columns and leaves the items in the table project_task_subtask, which no model reads. Export them first if they are needed.
  • The project flag does not come along: tick AI-driven Project again on each project.
  • The views of project_software and its two checklist message subtypes are replaced by new ones.
  • Between the two steps every page the module adds to the task form shows twice, and each start of the server logs that project_software cannot be loaded.

Configuration

  • On a project, switch on AI-driven Project (Settings tab, Tasks Management) to show the Technical Solution and Pull Requests tabs and the Resolution on its tasks, and to hide the core priority star on them.
  • Below it, on an AI-driven project, Stages Requiring a Resolution lists the stages a task enters only with a Resolution, and with a pull request when the Resolution is Code. Only stages of the project can be picked. Leave it empty to switch the closing rule off.
  • Below that, Stages Requiring a Type and an Estimate lists the stages a task enters only with a task type and an estimate above zero hours. Only stages of the project can be picked. Leave it empty to switch the estimate rule off.
  • What creates a task straight into a stage of that second list without both values is refused there: the kanban quick create, which takes a title and assignees; an email to the alias of the project, which gives neither value; a sales order line that creates a task, which gives no task type. A copy that keeps the stage of its source, a plain Duplicate or the duplication of a project, takes the type and the estimate of its source, so it is refused only where its source sits in such a stage without them.
  • Checklist items, question rows and test cases are managed by users with the User access of Project (Settings > Users, the Access Rights tab of a user), a checklist item and a question row only by a user who can read its task. The Checklist, Test Cases and Technical Solution tabs are hidden from users without that access.
  • Project > Task Notes and the Notes button of the task form are shown to users with the User access of Project. They list the notes of the tasks the user can read.
  • Pull requests are read by every internal user and created and edited by users with the User access of Project. No access right allows deleting one.
  • The stage log is read by system administrators (base.group_system) only. No access right allows creating, changing or deleting a row.
  • To be notified of checklist items of which you are neither the assignee nor the reviewer, edit your follower subscription on the task or on the project and tick All checklist updates.
  • An integration that writes tasks or checklist items passes mail_auto_subscribe_no_notify in the context to keep the write silent: no assignment notification, no checklist post. Without the key the notifications are queued as for any user, also for an account that has no email address to send them from.

Usage

On the task form, which opens on Description:

  • Set Priority, Estimate (in hours) and Task Type next to the tags. Size shows the size of the estimate and cannot be edited.
  • Checklist tab: add items, each with an Assigned to user, yourself unless you pick another, and an optional deadline. You are the reviewer of the items you add. The assignee or the reviewer moves an item with the state icons (TODO, Waiting, Done, Cancelled), changes its description or gives it another assignee. The task’s kanban card shows your own completion percentage, only when you have non-cancelled items assigned to you.
  • Technical Solution tab (AI-driven projects): the Questions list, then the Solution. Add a row per question, with its round and the user it is addressed to, and drag the rows into order. Give a row its answer and it becomes Answered, stamped with your name and the time; the status of a new row follows its answer. Once the row is saved, set it back to Open to ask again, or to Dropped when it no longer applies. The Answer column is hidden in the list until you show it. On a phone the list shows cards.
  • Test Cases tab: add ordered cases with steps and expected results, then give each case its result with the icons of its row; a row offers the states other than its own (Passed, Failed, Not run, Waiting, Not applicable). Verified by and Verified on show who gave the last Passed or Failed. On a phone the tab shows cards with the same buttons. Set Verification to Automated test or Demo, and the Automated test reference, on the form of the case.
  • Notes button: counts the notes of the task and opens them in the Task Notes list. It shows once the task has a note.
  • Pull Requests tab (AI-driven projects): add the pull requests of the task. The list shows the link, state, merge date and deploy date of each. A pull request already recorded for another task is picked from the list instead of being created again. PR (old value) shows above the list on a task that has one.
  • Resolution (AI-driven projects), next to the tags: choose it before moving the task to a stage that requires one. Code needs a pull request on the task; a task that already has one gets Code by itself.
  • Task Type and Estimate (AI-driven projects): set both before moving the task to a stage that requires them. The refusal names what is missing.

Project > Checklist lists the checklist items of the tasks you can read in the selected companies, opened on your own TODO items. Group by project, task, user or status.

Project > Test Cases lists the test cases of all tasks, opened on the ones Not run: a list, cards on a phone. Filter on Not run or Failed, group by project, task, status or verification. The header of a case’s form gives it its result with the same buttons, next to its status bar: Not run, Passed and Failed, and the status of the case when it is another.

Project > Pull Requests lists all pull requests, the newest first: a list, cards on a phone. Search by URL, repository or task, filter on Open, Merged, Closed or No State, group by repository or state. On the form of a pull request, set State, Merge Date and Deploy Date when it is merged and deployed.

Project > Task Notes lists the internal notes of the tasks you can read, archived tasks included, the newest first: a list, cards on a phone. A note of files alone is listed; a message to one user and a change of tracked fields are not. Filter on a category, search by contents, task or author, and group by category or by task: a task’s group bears its current name. A note opens read-only with its files, and Open Task opens its task. Nothing is created, changed or deleted from this menu.

To give a note a category, log it on the task with the category in bold as its first words, alone in the bold or followed there by a dash, a colon, a slash, a plus or an opening parenthesis: Design Decision - keep the flow; Progress: 2/3.

A tool that writes over RPC sets pr_uri on the task to the link of the pull request, one link per write, or resolution to data, configuration or no_change when there is none. A write of another link adds a second pull request to the task. The estimate is written to allocated_hours and the type to task_type; a tshirt_estimate sent with them is ignored. The estimate is a finite number: a NaN or an infinity is refused, in any project.

A tool that keeps a checklist over RPC creates project.task.checklist.item records with task_id, name and user_id, which defaults to the tool’s own user, and reads the items of a task from checklist_item_ids. It moves an item by writing state (todo, waiting, done or cancelled) as the item’s assignee or reviewer. It reaches only the items of the tasks its user can read; without allowed_company_ids in the context, those of all the user’s companies.

A tool that keeps the questions of a task over RPC creates project.task.question records with task_id and question, and round, addressed_to_id and answer when it has them, and reads the rows of a task from question_ids. It answers a row by writing answer; state takes open, answered or dropped. A create or write that makes a row Answered fills answered_by_id and answered_on unless it sends them. It reaches only the rows of the tasks its user can read.

A tool that gives test case results over RPC writes state on project.task.testcase: not_run, passed, failed, waiting or not_applicable. A create or write of passed or failed fills verified_by_id and verified_on unless it sends them. It sends verification_kind (manual, automated or demo) and test_reference with the result: only the buttons set manual by themselves. The former values todo, done and cancelled are taken as not_run, passed and not_applicable. passed is read, not written: a value sent for it is dropped, and passed true without a state gives passed.

A tool reads the notes of one category of a task with search_read on mail.message, the domain [("task_id", "=", <task id>), ("note_category", "=", "design_decision")] and fields such as date, author_id and body. note_category takes requirement_change, design_decision, bug_fix, review_fix, user_feedback, progress, revised or deploy. It reaches the messages its user can read, and groups them under the same check. It gives a note a category by posting it on the task with message_post, subtype_xmlid mail.mt_note and a body that opens with the category in bold, in a paragraph: <p><b>Progress</b> - in review</p>. A body of more than one node that opens with an inline tag and holds no block tag, such as <b>Progress</b> - in review, is stored inside a <span> and gets its category too.

The stage log has no view and no menu. A system administrator reads project.task.stage.log over RPC: the rows come ordered by date, each with task_id, previous_stage_id, stage_id, stage_name, date, user_id and source (live on every row this branch writes). The log holds the stages of every task, also of tasks a user cannot read: code that shows it to other users reads it with sudo(), for the tasks those users can read.

Known issues / Roadmap

  • The path of a pull request link is stored as written. Two spellings of one pull request (Owner/Repo and owner/repo, http and https, with and without /-/) are two records.
  • Nothing reads a pull request from its host: State, Merge Date and Deploy Date are set by hand or over RPC.
  • The closing rule and the estimate rule are checked on the tasks of a write that names their stage or their project. A stage recomputed for another reason is not checked, as for a subtask whose parent changes project.
  • A module that writes a task’s new project on its own, before the other values of the same write, runs both rules before the Resolution, the task type and the estimate of that write arrive. Setting them in an earlier write avoids it.
  • Neither rule is run when a stage gets marked or a project gets flagged, so a task can sit in a marked stage without what the stage requires: a Resolution, a pull request, a task type or an estimate. Such a task cannot be duplicated, and it stops the duplication of its project, until it gets it.
  • A recurring task cannot be set Done or Cancelled while the first stage of its AI-driven project is marked for the closing rule, unless the task sits in that stage: its next occurrence enters that stage without a Resolution, and the refusal takes the change of state with it. The same holds where that stage is marked for the estimate rule and the task has no task type or no estimate.
  • The priority star is hidden on the views the description lists. The portal keeps it: the project sharing views, the task list and the task page.
  • The task list of a flagged project drops its Priority column only when opened from the project, which tells it the project is flagged. Reloaded from its address, reached back from an embedded action or opened from a milestone, it shows the column with the stars hidden, as core shows its Milestone column there. A task opened from that list passes the flag on, whatever its own project: the Sub-tasks, Dependent Tasks, Tasks in Recurrence and parent task it opens have no Priority column, tasks of other projects included. The same task opened from another list passes nothing.
  • Leaving template status is not a change of stage: a task template undone, a project template turned back into a project or a template task moved to another project keeps its stage unchecked by either rule.
  • A sub-task that sits in a marked stage without what the stage requires stops a project template being made from its project, as it stops the duplication of the project: core creates its copy in that project first.
  • The sizes stored by an earlier 20.0 version of the module stay as they are until the hours of their task change: this branch has no migration that recomputes them.
  • An update from an earlier 20.0 version converts no data: test cases keep their former states, the former checklist items stay in a table nothing reads, and the Html questions and answers are deleted (see Installation).
  • The test case flag passed and the translation of the former state values (todo, done, cancelled) at create and write serve clients written for the former selection, until a later version removes them.
  • Question rows have no chatter: a change of status or answer leaves no trace but Answered by and Answered on.
  • A note whose category is in bold inside a heading or a list, or coloured, gets no category: only one opening <p> or <span> may come before the bold, and nothing between the bold and the category.
  • The eight categories and their spelling are fixed in the module: Bugfix or Deployment in bold is no category. A change of them gives existing notes a category only where a migration recomputes it.
  • A note that code logs with a change of tracked fields (_track_set_log_message) is part of the tracking message of the change: it gets no category and is not in Task Notes.
  • The stage log starts when the module is installed: the stages a task went through before that are not in it.
  • A row of the stage log is written when the change of stage is flushed to the database. Several changes of a task’s stage within one flush are one row, from the stored stage to the last one, and a change undone within one flush leaves none.
  • A stage written by raw SQL is not logged.
  • The user of a row is the one the update leaves on the task as its last writer. When the last writer does not change, that is the user of the environment that flushes the change: the acting user in an ordinary request, also under sudo().
  • The stage name of a row is the source-language name (en_US) of the stage when the row was written.
